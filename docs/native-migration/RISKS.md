# Risks

- macOS: no build or test has ever run; Qt Quick 3D rendering, packaging, signing and notarization are unverified.
- Viewport: no visual/performance comparison with the Three.js viewport; frame rate and VRAM unmeasured; large-STL behaviour untested.
- Bundled Python runtime and installer are not built; the app finds Python only via CRAFT_PYTHON or the dev interpreter.
- Windows MSVC and Windows SDK live on C: (pre-existing) / D:; no new C: footprint was added by this work.
- Pre-existing frontend failure: `scripts/checkBundleBudget.test.mjs` does not load on Windows (shebang parse error).
- Two analysis implementations (TS pull-direction vs Python) remain unreconciled.
- Manifold GitHub fetch happens at configure time; offline builds need a pre-populated `FETCHCONTENT_BASE_DIR`.
- Distance-field cavity offset: 8.6 s at 129k triangles and 12.8 s at 489k (1 mm clearance, Release, 8 cores). The banded distance shortcut relies on the offset surface being sampled at lattice spacing h and band = clearance + 4h; it is verified against the reference on 7 cases, not proven for every geometry. Dense lattice cache costs about 16 bytes per grid cell (up to ~200 MB at the 12M-cell budget). Not compared with the WASM timing.

- R-Master-1 Master Mold now follows every reference path the engine can reach (planar, height-field retry, grid and multi-label fallbacks, one-piece, localized core, multi-panel). Residual risk: the reference multi-label construction never succeeded on any fixture, so its success path is unverified against the reference (only failures match, with exact error text); the volumetric constructor mode is unported (engine never reaches it). Do not expose Master Mold in the UI as parity-complete until real-part coverage grows.
- R-Reports-1 (Largely addressed, see R-Analysis-1.) The Python detailed mold analysis was slow on large parts: a closed 10,800-face box took 561 s. It now takes 3.6 s, and a 5,120-face smooth sphere 21 s (ANALYSIS_PERFORMANCE.md). Parts with many distinct face normals still grow faster than their face count.
- R-Reports-2 The report registry marks Pull Direction "Coming Soon" (the reference data) while the same panel now shows a real Python result for it; the labels are the reference's and have not been reconciled.
- R-Reports-4 Generation readiness is "blocked" for every analyzable part today: the Python engine never selects a parting strategy (it leaves them for manual review) and the reference adapter treats a missing selection as a missing required input. That is the reference behaviour, so native shows it, but it means the readiness gate cannot be passed from real data yet; nothing downstream (Chapter 10 generation) consumes it either.
- R-Reports-5 The cavity analysis is the engine's shell/topology heuristic and says so itself: it cannot prove the absence of an internal cavity. Its output must not be presented as a proven "no cavity" result; the panel shows the engine's own caveats.
- R-Project-1 Format 1.0 is the first version: there is no real older format, so the migration chain is empty and only tested with injected steps. The first real format change must add a real migration with a fixture of the old file.
- R-Project-2 Opening and autosaving hold whole models in memory several times (file bytes, parsed soup, grounded copy; and the re-encoded STL when saving). A 48 MiB project saves in about 2 s and opens in under 1 s; the 512 MiB import ceiling has not been exercised, and autosave re-encodes and re-hashes the whole model every time it runs (60 s, only when dirty), not incrementally.
- R-Project-3 Crash recovery was first tested only by leaving a controller without a clean exit. It is now also tested with a real kill: `scripts/native/crash-drill.ps1` starts the application as a victim that keeps editing with a very short autosave interval, kills it with TerminateProcess at a random moment, and starts it again to recover (Windows, release build; D-103). 26 rounds recovered correctly (6 on the 20-triangle bracket, 20 on the 62.5 MiB, 1.3M-triangle sphere, where a kill lands inside a multi-second write about half of the time): an offer, a project that opens, the right model, and an edit state the victim really wrote, every time, so the atomic write holds. What the kills did find: a killed write leaves QSaveFile's temporary file (`<id>.craft.<6 characters>`, up to the whole project, 32 or 62.5 MiB) in the autosave folder forever (fixed, D-103). Still open: the same leftover next to the user's own file when a manual Save is killed is not cleaned (the folder is theirs); this is a process-level kill, not a power cut or an operating-system crash, so durability of the rename itself (no explicit flush) is still trusted to the OS; the drill is Windows-only and not in ctest.
- R-Project-4 Reopening a project rebuilds the mold automatically, which takes as long as generating it did (seconds for the bracket, much longer for heavy parts); there is no progress UI specific to restore. Master Mold sets and analysis reports are not rebuilt.
- R-Project-5 The app writes embedded projects only; linked projects are supported on read (with relink) and tested, but nothing in the UI creates one. The new File menu, dialogs and recovery/relink prompts were exercised through the controller and a clean headless run (no QML warnings), not by clicking through them on screen.
- R-Reports-3 (Closed 2026-11-20.) The Engineering reports section was looked at on the UI tour's capture of the mold-generated-and-analysed state (light theme, the inspector at its 320 px width): the Pull Direction card, the moldability summary, cavity analysis, generation readiness and the registered reports are laid out in order, wrapped, and nothing is cut off; the tour's lint reports no truncation or clipping in any state. One theme and one width were looked at in full detail.
- R-Master-2 Kernel triangulation can differ between the native and WASM builds for pin faces (D-029); anything keyed on triangle indices (sampled accessibility, mesh hashes) can move slightly.
- R-License-1 (blocking for any release) The Qt SBOM records Qt Quick 3D 6.8.3 as `Commercial OR GPL-3.0-only` (not LGPL); Qt Base, Declarative and Shader Tools offer LGPL-3.0. The viewport is built on Qt Quick 3D, so distributing Craft with open-source Qt needs a commercial Qt license or releasing Craft under the GPL-3.0. Craft's own license is also unchosen. The package is internal-test only until the product owner decides (`licenses/THIRD_PARTY_NOTICES.txt` says so). Engineering inventory only, not legal advice.
- R-Packaging-1 No Windows installer exists (MSI not built, D-055): no Start-menu entry, uninstaller, `.craft` association or upgrade handling. Not signed (SmartScreen will warn), no update mechanism, no native CI job; macOS packaging is not started and nothing was run on macOS.
- R-Packaging-2 The Python runtime hash is trust-on-first-use (D-051). Verification covers the Windows layout on this machine (a clean-profile hostile environment, not a separate clean VM); a machine without the MSVC runtime installed relies on the app-local copies, which the dependency check confirms are present but which were not tested on a bare OS image.
- R-Export-1 Exported tooling is in the model's world frame, not oriented for printing (D-059); the user (or a slicer) must orient and support it. Nothing here measures printability beyond the engine's own watertight/manifold/build-volume flags.
- R-Export-2 When the engine reports `unportedPathsReached`, the exported set may be missing options the full planner would try. The manifest records this (`completeness`) and the panel notice stays visible, but the files themselves look complete.
- R-Export-3 Not covered: the folder dialog, the panel layout and "Show folder" were not exercised on screen; paths longer than Windows MAX_PATH, network/removable drives and read-only folders are untested (only an uncreatable folder is); pieces of several million triangles were not timed. macOS is unverified like the rest of the app.
- R-Selection-1 Not pixel- or scene-compared with the Three.js viewport: the geometry and the picking are compared with the real reference code, the rendering (dashed look, overlay blend, emissive glow) was inspected by eye in both themes only. With the reference's 0.35 mm dashes the box looks nearly solid on large parts at normal zoom, as in the reference.
- R-Selection-2 Hover runs a ray cast against the part, linear in its triangle count, throttled to one per 33 ms. It was not timed on multi-million-triangle models.
- R-Selection-3 Escape clears the selection through a window shortcut, so pressing it to cancel typing in a text field also clears a selection (nothing else). Selection state is not part of the project file.
- R-SpruePreview-1 Not pixel-compared with the Three.js viewport; rendered and inspected in both themes only. The glass outline uses the native feature-edge extractor (exact float positions, 1 degree) where the reference's EdgesGeometry hashes vertices to 4 decimals, so a mold body with near-coincident vertices could outline differently. The glass applies to every visible mold body (the reference skips bodies flagged `cavityAffected: false`; native has no such flag).
- R-SpruePreview-2 The reference fixture only has entry necks shorter than the stem, so the neck clamp (`min(neckLength, stem)`) is checked by a unit test written from the reference source, not by a reference run. The preview recomputes the placement (a ray against every mold body) on each pointer move at most every 16 ms; it was not timed on molds with millions of triangles.
- R-SprueGizmo-1 Not pixel-compared with the Three.js viewport; the rings, label and editor were rendered and inspected (the active ring mid-drag, hover hiding the owning body) but the editor popup's look and keyboard focus behaviour were not inspected on screen. The overlay View3D is a second render pass; its cost was not measured on large molds.
- R-SprueGizmo-2 The QML routing is covered end to end by one smoke test that sends real platform mouse events (press-drag-release and double click); Escape, Shift-held drags, the right/middle buttons and pointer cancellation reach the controller through the QML but were exercised only through the controller API. That smoke test uses Qt's private platform event interface and is compiled only in test builds (CRAFT_BUILD_TESTS), so a packaged build cannot run it.
- R-SprueGizmo-3 There is still no sprue undo/redo and no result caching, so every resize re-evaluates the sprue stage. Rings of a pending sprue show the requested diameter only until the evaluation finishes; if the evaluation fails the ring returns to the last resolved geometry only through the normal rebuild.
- R-CutPlane-1 Removing a plane cannot be undone: the reference pushes a history entry (undo/redo over every cut-by-face edit) and native has no such history, so a removed plane's position is lost (re-choosing the face gives its default). This is the same gap as sprue and segmentation undo/redo.
- R-CutPlane-2 After a removal the reference immediately shows the rebuilt mold parts (cheap); native drops the generated mold and the user regenerates, which for a large part includes the cavity. Not pixel-compared with the Three.js viewport; the slabs are depth-tested with depth writes off, as the reference's material, and were inspected on screen in the dark theme only.
- R-CutPlane-3 The reference also lets a plane be dragged with the right mouse button (and then adopts the new position); that drag is not ported (the open "plane drag UI" item). The Eraser click was exercised through real mouse events only for the primary button; the eraser cursor is the reference's SVG path approximated with curves.
- R-Undo-1 Body-visibility toggles are recorded by the reference and not by native (D-073), so after toggling visibility the reference's Undo first reverts that toggle; native's does not. Revisit if users expect it.
- R-Undo-2 The mold-generation step differs by design: the reference undoes into a parts-ready stage, native into the inputs without a mold (D-073); the fixture covers inputs and depths, the derived 4-to-2 bodies scenario is checked by a native test of its own rather than by number against the reference.
- R-Undo-3 A snapshot shares large results, so up to 50 generated molds can be kept alive at once (memory). They are shared, not copied, but a long session of regenerate-edit cycles holds each distinct mold until it falls off the stack. No measurement of the footprint has been made.
- R-Undo-4 The cancel call in undo is not covered by a test that can fail: dropping it leaves behaviour unchanged, because the generation counter already discards the late result. It only frees the CPU sooner.
- R-E2E-1 The end-to-end journey runs one real part (the 9,024-triangle sphere used by the reference's e2e suite) through a design with one cut face and one sprue. It does not cover the Master Mold, segmentation, the analysis worker, a printed-part-scale model or a linked project, which are tested separately. It takes about 40 s in Debug.
- R-E2E-2 The test proves the exported files are well-formed binary STL (size = 84 + 50 x triangles) and identical across save/reopen; it does not load them in a slicer or compare them with files from the reference app.
- R-Viewport-1 Colour and lighting are close, not identical: after the look was aligned (D-082) the colour difference inside the part is 0.025 to 0.031 (of full scale) and the similarity 0.60 on the flat box and 0.79 to 0.84 on round parts, against 0.12 to 0.17 and 0.49 to 0.72 before. The reference also shows a moire pattern on flat faces (probably shadow-map self-shadowing) that native does not reproduce, and shadows were not ported (a ground shadow was not verified in the reference).
- R-Viewport-2 All numbers come from one machine: an Intel UHD 620, a 75 Hz display, one viewport size (960 x 640), one orbit path, three runs per scene, no confidence intervals. A discrete GPU, another refresh rate or a large viewport can move the crossover between the two renderers or hide the fixed cost below. Nothing is claimed for macOS.
- R-Viewport-3 Native spends about 4.4 ms per frame (about 215 fps uncapped) regardless of the part, from 12 to 405,000 triangles (5.5 ms before the imported part's edge lines were removed), against 1.4 ms for the reference on a small part. It is invisible at 60 or 75 Hz and probably comes from the rest of the Qt Quick window (two 3D views, the inspector, toolbars) and the swap chain, but it was not profiled. Native also shows one slow frame (about 25 ms) per orbit run, not investigated.
- R-Viewport-4 (The ruler and hint badge named here earlier are now ported, D-084.) Automatic part orientation (`automaticModelOrientation`, `partOrientation3dRuntime`: an Orient action that lays a part on its best face, and manual rotation) exists in the reference and has no native equivalent or parity row. Not investigated beyond finding it while reading `localStlImport`.
- R-Viewport-5 The measurements are tooling-grade: the reference runs in headless Chrome with synthetic pointer events and a pixel readback, native in a real window; the two cadence protocols are comparable in intent, not identical (D-079). The pixel mask includes the reference's yellow axis labels where they touch the part in the dark theme, which inflates the boundary-distance columns there; IoU, area and centroid are not affected the same way. The test-only code in the native executable (`CRAFT_BUILD_TESTS`) is compiled into the Release build used for timing.
- R-Viewport-6 A STL with zero facet normals renders black in the reference and lit in native (native recomputes them). Harmless for native, but it means such files look different in the two applications.
- R-Smoke-1 (Re-examined 2026-11-19; the three original failures are unexplained and were not reproduced, but one real mechanism for exactly this kind of failure was found and closed.) The real-event smoke tests failed three times in full runs: `app_smoke_eraser` twice on 18 November and `app_smoke_hint_events` once on 19 November; they passed in every rerun. Both tests were hardened (they poll, and their messages carry the state), and `scripts/native/smoke-stress.ps1` ran 217 test runs without a failure (idle, all CPUs busy, a dialog in the foreground). The mechanism found later the same day: the smoke tests shared the user's real autosave folder, a run that ends without a clean shutdown leaves an autosave there, and the next launch opens with the "Recover unsaved work?" dialog over the window, which swallows every synthetic mouse press: six tests that send real mouse events failed together after the UI tour had left autosaves (found by bisecting code identical to the last green run; deleting the three stale files fixed it). Fixed: every smoke test has an autosave and cache folder of its own, isolated runs discard stale recovery state, the comparison script and the tour wrapper isolate too; proved by planting an autosave in the real folder (all eight smokes pass, the file is untouched). No smoke test leaves an autosave behind when it runs (checked after each of them, two rounds), so this does not explain the original three. The Bad Image dialog of the kernel tests (R-Analysis-9) is a second candidate for the hint failure. If one fails again its message carries the state.
- R-Viewport-7 The reference's hemisphere light and RoomEnvironment image-based light are approximated in native by an ambient term, a light from straight above and the key/fill/rim rig, with Qt's brightness scaled by I / pi times the exposure (calibrated against the frames, not derived). Specular highlights, glass and the other part roles (registration keys, sprue funnels, cavity surfaces) were not compared with the reference. A lighting change in either renderer can move the numbers.
- R-Viewport-8 Mold bodies are now all the reference's red (D-082). Native used to give each body its own colour from a six-colour palette, which made adjacent bodies easy to tell apart; the reference does not. With several bodies the only cue is now the geometry and the edge lines. If this is missed it is a native addition to bring back deliberately, not a parity fix.
- R-Viewport-9 Timing runs can be disturbed by something on the machine: in one full run two of three runs of one scene read 61.7 and 59.5 fps with a 60 ms stall while the same scene in the other theme and six reruns were clean at 74.7 fps. The cause was not found. Medians of three absorb one bad run, not two, so a surprising number should be rerun alone before it is believed. It happened again on 2026-11-19: the first full re-measurement read 67 to 71 fps on the small scenes and 5.3 to 5.6 ms per frame uncapped (74.7 fps and 4.3 ms before and in the rerun), the identical command run again was clean, and the cause was not found. Between days the machine moves too: the torus under the display's cadence read 74 fps on 18 November and 58 fps on 19 November with an unchanged older build. A claim about a change therefore needs an alternating A/B of the two builds (`scripts/native/ab-viewport.ps1`).
- R-Ruler-1 The ruler's labels sit within a few pixels of the reference's, not exactly on them: the label font is the platform's (Qt semibold) against the browser's `system-ui` 600, so label widths differ, and the reference measures the zoom with the previous frame's camera while native uses the current one. Whether the labels overlap the part the same way was only checked by eye in two scenes.
- R-Ruler-2 (Resolved 2026-11-19.) The timing and memory tables were re-measured with the ruler: run side by side with a build of the commit before it, the ruler costs no frame time that could be measured (4.2 to 4.6 ms per frame against 4.3 to 5.0 ms uncapped; the same 74.7 fps at the display's cadence on the box and the 9k sphere). The sporadic dips of the torus scene are R-Viewport-10.
- R-Viewport-10 Against the build from before the ruler, the current build shows sporadic dips on the torus scene at the display's cadence: 5 of 18 runs at 47 to 56 fps where the older build had none (medians 58.2 and 58.5, 18 runs each, alternating). The uncapped cost, the other scenes and the median are the same. The ruler, the hint badge, the plane hover and the other commits since are all candidates; none was singled out and the dips were not investigated (a profile of the frames with the ruler and the badge switched off one at a time would separate them).
- R-Ruler-3 Native's coloured X/Y/Z axis lines are gone (the reference has none). They showed which way Z points; the ruler shows the X and Y axes and their scale only, and with the Axes option off nothing marks the axes at all.
- R-Ruler-4 The label images are written to the cache directory (`ruler-labels`, named from the font and the text) once per process. If the directory cannot be written the labels do not appear (the quads would be empty) and nothing reports it.
- R-Analysis-1 (CLOSED by D-089: the candidate evaluation runs in a native kernel; 20,480 smooth faces 294 s -> 2.8 s.) Parts whose faces all have different normals (smooth, high-polygon meshes, scans) still cost candidates x faces evaluations: 1,280 to 5,120 faces took 2.8 s to 20.7 s, so a smooth 20,000-face part would take minutes (not measured) and may approach the 20-minute job timeout at tens of thousands of faces. Removing that changes what is computed (fewer or merged candidates), so it is not a behaviour-preserving fix; the one that is, is a native reimplementation of the candidate evaluation.
- R-Analysis-2 The speed-up modifies the Python engine, which was the behavioural reference. Equality with the original is shown by tests, a field-by-field comparison of the worker payload against the commit before the change on four models, and stage fingerprints on six, all on generated boxes and spheres on one Windows machine. The argument that the hierarchy returns the brute-force answers rests on IEEE-754 double arithmetic applied in the same order (true for CPython floats) and on monotonic rounding in the box test; it is not formally proven. A part with real undercuts and many occluded faces was not measured.
- R-Analysis-3 With `retain_face_evaluations=False` a candidate's per-face evaluations are gone. Nothing in the engine reads them after scoring, and the worker reports only counts, but a future consumer that reads them from a worker-built report gets a `FaceEvaluationsNotRetainedError`, by design and loudly, not an empty list.
- R-Analysis-4 The hierarchy is built once per query backend, and the engine builds three (the detailed undercut stage and two cavity stages), so a very large mesh pays for three builds (the build is a sorted median split, a fraction of the ray queries on the sizes measured). Sharing one built hierarchy per model would remove two of them; not done.
- R-Analysis-5 On large smooth meshes the ray queries (run in Python through the hierarchy, 100,000 rays for 5,120 faces) and the report's JSON now dominate: the 20,480-face sphere takes 43 s and 449 MiB, a model of 100,000 faces would take far longer (not measured). A native ray query would have to reproduce the brute-force answers bit for bit like the hierarchy; not started.
- R-Analysis-6 The kernel is a second implementation of the evaluation loop (C++ next to the Python), equal to it today by tests, a load-time check and mutation checks (15 of 17 deliberate bugs caught, 2 change no bit). A future change to the Python loop (a different clamp, another summation order) must be made in both; the check fails loudly on the next worker start (the kernel is then refused and the Python loop runs, logged), but a silent fall-back to Python is a performance loss that only the log and the `diagnostics` field show. Test: `py_native_evaluation`.
- R-Analysis-7 Only a Windows kernel (MSVC, Release) has been built and run. The Linux and macOS build rules exist (`-ffp-contract=off`, pthreads, `.so`/`.dylib` names in `AppPaths.cpp`) and have never been compiled; macOS validation was stopped at the user's request. Bit-for-bit equality with the system's `asin` on another C library is exactly what the load check is for, and has not been exercised there.
- R-Analysis-8 The kernel uses up to 8 hardware threads (16 at most) for the seconds that an evaluation takes, which competes with the UI on a small machine. The loop is short enough (2.8 s for 420 million evaluations) that this has not been tuned, and a thread count cap or a lower thread priority was not added.
- R-PlaneDrag-1 Reproduced from the reference: looking exactly along a plane's axis (straight down at a z plane, exactly along x or y for those planes) the reference's drag plane has no normal, a press either does not start or the plane does not move. The native port does the same (recorded: `topDown`, `alongX`, `alongY` scenarios). A user who looks straight down and right-drags a horizontal plane sees nothing happen; the sliders still work, and a slightly tilted view works. Not "fixed" because the migration reproduces the reference; changing it is a product decision.
- R-PlaneDrag-2 The drag was compared with the real runtime on rays (every event carries the world ray and the camera's view and up vectors), so it does not check the camera: pixel to ray in the native camera is covered by the existing picking tests, and the app-level tests and the smoke test run the drag through the native camera, but no recorded reference pose was replayed through the native camera for the drag itself.
- R-PlaneDrag-3 Cursor precedence over the part and the tool cursors is a judgement (D-093). Hover while orbiting changes the plane's look under the pointer, as in the reference, which can look like flicker when a plane is crossed during an orbit.
- R-PlaneDrag-4 Not ported: the reference also lets a Segmentation extension plane be dragged (`moveSegmentationExtensionAxis`); native has no such planes yet (the open item "3D dragging of extension planes"). A drag in the reference is blocked while a multi-body session owns the model; native reaches the same state by hiding the planes under an adopted segmentation.
- R-PlaneDrag-5 Not tested: a drag while a mold generation is running. The reference does not block it either (it blocks removal), and native's slider does not; `invalidateMoldInputs` cancels the running generation as it does for any input change.
- R-Analysis-9 Fixed in this session, kept as a record: loading a corrupt or wrong-architecture kernel library made Windows show a modal "Bad Image" box and the worker waited for it (an unwatched worker would hang until the job timeout). The loader now suppresses the box for the load (thread error mode), and a test checks it. - R-Cavity-1 Making High the default (D-096) matches the reference but is much slower and larger on dense parts. Release, 1 mm clearance, one split, sphere parts (`bench_pipeline <dir> 1.0 high|standard`): 2,208 triangles 121 ms against 72 ms; 25,280 triangles 1.0 s against 0.55 s; 128,880 triangles 43 s against 8.7 s (peak 622 against 157 MiB); 488,600 triangles 51 s against 12.4 s (749 against 336 MiB). The distance-field cells go from at most 12 million to 24 million and the tool from 173k to 707k triangles. Not compared with the reference's WASM time (none was measured), so how much of the wait the reference also has is unknown. Mold generation shows a progress stage but a 50 s wait for a dense part is a real cost; Standard is one click away. A part that exceeds the High grid budget is refused with the existing grid-budget error, not silently downgraded.
- R-Smoke-2 `app_smoke_master` failed once with "a click on the Master Mold button did not start generating" during a mutation run (the first launch after a rebuild), and passed in 31 of 31 other runs (8 + 3 + 20 plain, and the mutations); not reproduced and not explained. If it recurs, suspect the first click arriving before the toolbar binding settled after a cold start.
- R-SprueCache-1 The cache keeps a copy of each sprue's result, including the updated bodies' meshes (a copy per sprue of every body it cut into), until the next evaluation replaces it or a new model is imported; for dense molds with several sprues that is memory, not measured. Clearing on import has no test (it cannot change a result: the keys would not match across models). The saving was measured only on a small mold: three sprues on a 20 mm cube cavity take 23.5 ms computed and 0.06 ms from the cache (Release); a dense cavity, where each Boolean pass costs far more, is expected to gain more and was not measured. R-SprueGizmo-3's "no result caching" is resolved by this.
- R-SegPreview-1 The preview registration cannot be cancelled once started: a plan replaced while it runs leaves the job running to its end. Measured (Release, bracket, plan and preview): 8 sections 31 ms, 27 sections 32 ms, 64 sections 32 ms, 180 sections 111 ms, 512 sections 496 ms, so the cost is small and nothing waits on it; a part whose plan has many large, keyable interfaces could take longer, and quitting the application would wait for such a job (the same property as the other worker jobs).
- R-Master-2 Master Mold's multi-label construction has never been seen to succeed, in the reference or in native (0 of 9 reference attempts, D-102). - R-FileJobs-1 Cancel granularity and what was measured. Reading, hashing and writing stop within a chunk; STL parsing and building the loaded model are single calls, so a stop that arrives during one waits for it to end. Measured on the 62.5 MiB, 1.3M-triangle part (Release): an import, a save and an open each stopped 31 to 47 ms after the cancel, a save cancelled halfway left no file, a full save took 2.2 s and reported progress about 108 times. Not measured: the same at the 512 MiB ceiling, where parsing could be a long single call. The backup copy of the previous file (`.bak`) before a save is one `QFile::copy` and is not interruptible. The branch where a stop arrives after the work has finished (the result is kept) is untested, since it cannot be forced without a hook; the tests hold the only worker thread to cancel before the work starts and the core tests cancel inside every stage. The footer's layout while a job runs is not in the UI tour (nothing in the tour runs long enough to capture it).
- R-LargeStl-1 Measured at the 512 MiB limit (Release, UV spheres made by `scripts/native/viewport/makeLargeModel.mjs`, Intel UHD 620, 15.9 GiB RAM, one machine). 10,734,000 triangles, 511.8 MiB: import 2.2 to 2.5 s with at most 23 ms of UI-thread stall, peak 1.5 GiB, a frame renders; a project save 13.0 s (peak 2.5 GiB), open 14.9 s (peak 3.5 GiB), a cancel of import, save or open stops in 42 to 52 ms; the 516 MiB file is refused in 2.1 s. Where the 13 to 15 s go: SHA-256 of 512 MiB takes 3.1 s (about 170 MB/s) and a save does it twice (once to fill the model record, once to verify before writing), writing 512 MiB takes 4.8 s, encoding 0.2 s, parsing 0.3 s; an open hashes once and also writes the 512 MiB model to the analysis cache (`materializeModel`). None of that is wrong, only slow, and the progress bar and Cancel make it bearable; skipping the second hash or deferring the cache write would save about 3 s and 5 s. Mold generation does not scale (D-105): 1.31M triangles 12 s and 1.6 GiB, 2.64M 47 s and 3.1 GiB, 5.20M 74 s and 6.3 GiB (whole smoke run), 10.73M past 9.2 GiB without finishing in 116 s, so it is refused when it cannot fit. Not measured: the orbit rate and GPU memory at 10.7M triangles (it renders on an integrated GPU, but how smoothly is unknown), the Master Mold, segmentation, the Python analysis and sprue evaluation at that size (only the mold has the guard), and geometry other than spheres (a part with fine features may need more per triangle than the estimate); the estimate is a straight line through four points on one kind of part. The memory probe is Windows and Linux only and sees only what is free when the mold starts, not what other programs take while it runs.
- R-Master-3 Measured (Release, 2026-11-20, one machine, memory is the peak working set of the test process): Master Mold on a 20,000-triangle sphere took 93 s and 0.19 GiB; on a 405,000-triangle torus 87 s and 2.83 GiB; on spheres of 82k, 160k and 640k triangles it had not finished after 250 s (0.63, 1.14 and 0.83 GiB at that point) and on the 1.31M-triangle sphere it passed 9.2 GiB without finishing. So how long it takes and how much it needs depend on the geometry more than on the triangle count, and free-form parts are slow even when small (the reference's own tests allow it 5 minutes). The 9 KB per triangle estimate is a line above four observations; a part not like these can need more. An abandoned run (D-106) keeps its thread, its CPU and its memory until its Boolean returns, which can be minutes, and nothing bounds that: the memory guard looks only at the start of a run. The mold's own Cancel, input changes and undo are covered the same way by D-107. Not measured: the Python import analysis's memory (the process-tree measurement missed the worker, a grandchild behind the venv launcher), though it took 43.5 s on the 1.31M-triangle part and the moldability analysis did not finish in the smoke test's 120 s there. Two protections in the abandon path (cancelling the token, ignoring late progress reports) hide each other in any test, so neither has a mutation of its own that is caught.
- R-Test-1 Until 2026-11-20 "all tests pass" meant the Debug configuration. The first complete Release run (`ctest --preset windows-release`) found two problems that Debug cannot show: a test that only passed in Debug (`droppedFilesAreValidatedLikeTheReference` created its files inside `Q_ASSERT(file.open(...))`, which a Release build compiles out, so the files never existed; fixed, and no other side-effecting assert exists in the sources) and a timeout that could never be met (`tst_master_equivalence` runs its Master Mold fallback rows only in Release and took 1006 s, against the shared default of 300 s; it now has its own 1800 s). After the fixes the two tests passed in Release one by one (17 minutes in all); one complete Release `ctest` in a single run was not repeated. The Release run is slow (about 2 minutes for the suite plus 17 for that one test) and is not in any automated job: there is no CI (the checked-in workflow was not verified to run ctest), so a Release-only failure can again go unseen until someone runs it by hand.

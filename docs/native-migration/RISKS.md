# Risks

- macOS: no build or test has ever run; Qt Quick 3D rendering, packaging, signing and notarization are unverified.
- Viewport: no visual/performance comparison with the Three.js viewport; frame rate and VRAM unmeasured; large-STL behaviour untested.
- Bundled Python runtime and installer are not built; the app finds Python only via CRAFT_PYTHON or the dev interpreter.
- Windows MSVC and Windows SDK live on C: (pre-existing) / D:; no new C: footprint was added by this work.
- Pre-existing frontend failure: `scripts/checkBundleBudget.test.mjs` does not load on Windows (shebang parse error).
- Two analysis implementations (TS pull-direction vs Python) remain unreconciled.
- Manifold GitHub fetch happens at configure time; offline builds need a pre-populated `FETCHCONTENT_BASE_DIR`.
- Distance-field cavity offset: 8.6 s at 129k triangles and 12.8 s at 489k (1 mm clearance, Release, 8 cores). The banded distance shortcut relies on the offset surface being sampled at lattice spacing h and band = clearance + 4h; it is verified against the reference on 7 cases, not proven for every geometry. Dense lattice cache costs about 16 bytes per grid cell (up to ~200 MB at the 12M-cell budget). Not compared with the WASM timing.

- R-Master-1 Master Mold now follows every reference path the engine can reach (planar, height-field retry, grid and multi-label fallbacks, one-piece, localized core, multi-panel). Residual risk: the reference multi-label construction never succeeded on any fixture, so its success path is unverified against the reference (only failures match, with exact error text); the volumetric constructor mode is unported (engine never reaches it). Do not expose Master Mold in the UI as parity-complete until real-part coverage grows.
- R-Reports-1 The Python detailed mold analysis is pure Python and slow on large parts: 20 faces take milliseconds but a closed 10,800-face box took 561 s. The native job has a 20-minute timeout and can be cancelled, but real STLs with tens of thousands of faces will exceed that. Needs an engine-side performance fix (or a native reimplementation) before this is usable on production parts; not a bridge problem.
- R-Reports-2 The report registry marks Pull Direction "Coming Soon" (the reference data) while the same panel now shows a real Python result for it; the labels are the reference's and have not been reconciled.
- R-Reports-4 Generation readiness is "blocked" for every analyzable part today: the Python engine never selects a parting strategy (it leaves them for manual review) and the reference adapter treats a missing selection as a missing required input. That is the reference behaviour, so native shows it, but it means the readiness gate cannot be passed from real data yet; nothing downstream (Chapter 10 generation) consumes it either.
- R-Reports-5 The cavity analysis is the engine's shell/topology heuristic and says so itself: it cannot prove the absence of an internal cavity. Its output must not be presented as a proven "no cavity" result; the panel shows the engine's own caveats.
- R-Project-1 Format 1.0 is the first version: there is no real older format, so the migration chain is empty and only tested with injected steps. The first real format change must add a real migration with a fixture of the old file.
- R-Project-2 Opening and autosaving hold whole models in memory several times (file bytes, parsed soup, grounded copy; and the re-encoded STL when saving). A 48 MiB project saves in about 2 s and opens in under 1 s; the 512 MiB import ceiling has not been exercised, and autosave re-encodes and re-hashes the whole model every time it runs (60 s, only when dirty), not incrementally.
- R-Project-3 Crash recovery was tested by leaving a controller without a clean exit (the autosave file is what a crash leaves), not with an OS-level kill of the process; the write itself is atomic, so a kill mid-autosave leaves the previous autosave, but that was not tested with a real kill. Durability relies on the OS rename/flush behaviour of `QSaveFile`.
- R-Project-4 Reopening a project rebuilds the mold automatically, which takes as long as generating it did (seconds for the bracket, much longer for heavy parts); there is no progress UI specific to restore. Master Mold sets and analysis reports are not rebuilt.
- R-Project-5 The app writes embedded projects only; linked projects are supported on read (with relink) and tested, but nothing in the UI creates one. The new File menu, dialogs and recovery/relink prompts were exercised through the controller and a clean headless run (no QML warnings), not by clicking through them on screen.
- R-Reports-3 Not visually verified: the new Inspector section loads and binds (app_smoke, app workflow tests) but its layout was not inspected on screen.
- R-Master-2 Kernel triangulation can differ between the native and WASM builds for pin faces (D-029); anything keyed on triangle indices (sampled accessibility, mesh hashes) can move slightly.
- R-License-1 (blocking for any release) The Qt SBOM records Qt Quick 3D 6.8.3 as `Commercial OR GPL-3.0-only` (not LGPL); Qt Base, Declarative and Shader Tools offer LGPL-3.0. The viewport is built on Qt Quick 3D, so distributing Craft with open-source Qt needs a commercial Qt license or releasing Craft under the GPL-3.0. Craft's own license is also unchosen. The package is internal-test only until the product owner decides (`licenses/THIRD_PARTY_NOTICES.txt` says so). Engineering inventory only, not legal advice.
- R-Packaging-1 No Windows installer exists (MSI not built, D-055): no Start-menu entry, uninstaller, `.craft` association or upgrade handling. Not signed (SmartScreen will warn), no update mechanism, no native CI job; macOS packaging is not started and nothing was run on macOS.
- R-Packaging-2 The Python runtime hash is trust-on-first-use (D-051). Verification covers the Windows layout on this machine (a clean-profile hostile environment, not a separate clean VM); a machine without the MSVC runtime installed relies on the app-local copies, which the dependency check confirms are present but which were not tested on a bare OS image.
- R-Export-1 Exported tooling is in the model's world frame, not oriented for printing (D-059); the user (or a slicer) must orient and support it. Nothing here measures printability beyond the engine's own watertight/manifold/build-volume flags.
- R-Export-2 When the engine reports `unportedPathsReached`, the exported set may be missing options the full planner would try. The manifest records this (`completeness`) and the panel notice stays visible, but the files themselves look complete.
- R-Export-3 Not covered: the folder dialog, the panel layout and "Show folder" were not exercised on screen; paths longer than Windows MAX_PATH, network/removable drives and read-only folders are untested (only an uncreatable folder is); pieces of several million triangles were not timed. macOS is unverified like the rest of the app.
- R-Selection-1 Not pixel- or scene-compared with the Three.js viewport: the geometry and the picking are compared with the real reference code, the rendering (dashed look, overlay blend, emissive glow) was inspected by eye in both themes only. With the reference's 0.35 mm dashes the box looks nearly solid on large parts at normal zoom, as in the reference.
- R-Selection-2 Hover runs a ray cast against the part, linear in its triangle count, throttled to one per 33 ms. It was not timed on multi-million-triangle models.
- R-Selection-3 Escape clears the selection through a window shortcut, so pressing it to cancel typing in a text field also clears a selection (nothing else). Selection state is not part of the project file.- R-SpruePreview-1 Not pixel-compared with the Three.js viewport; rendered and inspected in both themes only. The glass outline uses the native feature-edge extractor (exact float positions, 1 degree) where the reference's EdgesGeometry hashes vertices to 4 decimals, so a mold body with near-coincident vertices could outline differently. The glass applies to every visible mold body (the reference skips bodies flagged `cavityAffected: false`; native has no such flag).
- R-SpruePreview-2 The reference fixture only has entry necks shorter than the stem, so the neck clamp (`min(neckLength, stem)`) is checked by a unit test written from the reference source, not by a reference run. The preview recomputes the placement (a ray against every mold body) on each pointer move at most every 16 ms; it was not timed on molds with millions of triangles.

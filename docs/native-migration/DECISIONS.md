# Decisions

- D-001 Renderer: Qt Quick 3D with custom geometry from `MeshGeometryAdapter`. No custom Dawn/Metal/Vulkan renderer; no measurements yet that would justify one.
- D-002 Toolchain baseline: Qt 6.8.3 msvc2022_64, MSVC 14.44 (VS 2022 Build Tools 17.14), CMake 4.4.3, Ninja, C++20, Manifold v3.5.1 (commit cc8a7f6; same release as the reference's manifold-3d 3.5.1), Python 3.13.17 for the worker.
- D-003 Manifold built without TBB and CrossSection (single-threaded like the WASM reference; no Clipper2).
- D-004 Native STL size cap is 512 MiB (reference 25 MiB, a browser limit).
- D-005 Geometry-version tokens hash bounds as float64 rather than JSON text; stable on native, not string-equal to reference tokens.
- D-006 (superseded in session 3) Positive cavity clearance is now ported; the only intentional deviation is that a cavity-outer-breakthrough blocker is reported with the reference's observable code `cavity_boolean_failed`.
- D-009 Manifold stays built without TBB. Level-set sampling is parallelised by the engine itself: the lattice Manifold samples is pre-evaluated on all cores into a dense cache (bit-exact position match, otherwise falls back to the SDF). Cancellation is polled every 1024 SDF evaluations by throwing from the callback; the first exception is rethrown after the workers join.
- D-010 The offset SDF is evaluated with a distance band (clearance + 4 lattice steps): beyond it only the sign is computed. LevelSet uses exact values only near the offset surface, and the equivalence tests confirm identical output.
- D-007 Analysis cancel/timeout kills the worker process; it restarts lazily.
- D-008 QML lives in `native/app/ui` (qmlcache cannot handle `../` paths).
- D-011 The derived body geometry-version token after a sprue is a native FNV hash over (upstream version, operation id, position, profile, mold revision); it is stable and input-sensitive but not string-equal to the reference token.
- D-012 A sprue can only be created where the placement ray reaches the cavity (the reference preview shows an invalid, red placement and the store would accept it; the native app refuses it with a status message).
- D-013 Sprue intents live in the controller, survive cavity regeneration (marked pending, re-resolved in the same job) and are dropped on a new import. The reference per-sprue result cache is not ported; sprue re-evaluation after an edit reruns every sprue.
- D-014 Ordering of bodies and of equal-area interfaces uses byte order of the id string; the reference uses localeCompare (ICU). They agree for the id shapes produced by the app (digits and punctuation differ only at the first differing character), and all 30 reference cases match; ids with letter case or accents could order differently.
- D-015 Registration ids hash the same strings as the reference, so interface and feature ids are equal to reference ids (JavaScript Number-to-string is reproduced in jsNumberToString). The dependency-snapshot revision and body version tokens are native digests (D-005).
- D-016 Registration always runs as the last derived stage, also with zero sprues and a single body; a non-generated registration is reported as a warning (same rule as the reference store).
- D-017 Segmentation ids hash canonical JSON with keys ordered by an ASCII approximation of ICU collation (case-insensitive primary, lowercase before uppercase on ties). All 18 reference cases reproduce the reference ids; non-ASCII or punctuation keys are not covered.
- D-018 Native Segmentation plans from the preliminary whole-block source only. Merging protected regions from a committed mold (readCurrentSegmentationSourceSnapshot) was not wired at first (done since: D-111); the committed-region builder exists as `protectedRegionsOf()` and is tested only through the protected-region planning cases.
- D-019 An adopted Segmentation result replaces Cut by Face: the cavity, sprue and registration stages run on the segmented bodies with segmentation lineage (partition-coverage check off, automatic registration sizing), and the mold clearance used is the automatic one (at least 100 mm).
- D-020 Plan preview shows planned section boxes only; the reference additionally generates a preview registration asynchronously.
- D-021 Planning-mesh cluster keys ("cx:cy:cz:face") are ordered with an ICU-like rule where ":" sorts before digits, to match the reference localeCompare; Math.hypot is reproduced with V8 compensated summation (`jsHypot3`) so normals agree to the last digit.
- D-022 Master preflight does not yet run the bounded self-intersection pass (a BVH triangle-pair test with three-mesh-bvh semantics). `selfIntersectionChecked` is therefore always false natively, so a self-intersecting mesh that the reference rejects is reported as valid or repairable here. This must be closed before Master Mold results are trusted.
- D-022 (closed) The preflight self-intersection pass is now ported (sweep over overlapping triangle boxes + a port of the three-mesh-bvh triangle test); it matches the reference on the overlapping-box fixture and is skipped above 20,000 triangles exactly like the reference.
- D-023 Accessibility rays use a native median-split BVH with a padded slab test and the three.js Ray.intersectTriangle arithmetic, not three-mesh-bvh itself; hit sets are identical on all fixtures but a ray grazing a box boundary within 1e-6 mm could differ.
- D-024 `icuLess` approximates ICU root collation for ASCII ids (punctuation < digits < letters, case-insensitive then lowercase first); `jsToFixed` reproduces JS toFixed (round half up on the exact decimal expansion).
- D-025 The planner is a stateful class (WorkingMoldPieceCountSearch) instead of a closure; it copies the planning mesh and analysis it is given. Parting-interface ids are ordered with icuLess. JavaScript Map/Set insertion order is reproduced with vectors where it affects results (piece area votes, adjacency).
- D-026 Working-mold geometryVersion is a native deterministic token (hash of the mesh version, direction and release order), not the reference value, which hashes a JSON of typed arrays; it is a stale-detection identity (same class of deviation as D-005).
- D-027 The planar constructor maps a source-mesh rejection to the reference WASM text ("Not manifold") so rejection reasons are identical; other kernel statuses keep their native wording.
- D-028 `tst_master_equivalence/constructionMatchesReference(cube-grid-large)` is skipped in Debug builds (QSKIP under !NDEBUG): a 50,700-triangle part makes every sweep a full Boolean and the Debug kernel exceeds Qt's 300 s per-test limit. It passes in Release (about 50 s for all construction rows). CI must run the Release build of this test.
- D-029 Kernel triangulation: native Manifold 3.5.1 and the WASM 3.5.1 produce bit-identical vertex positions on every Master piece, but on pieces with pin faces (coplanar faces with holes) the TRIANGLE CONNECTIVITY can differ (same vertices and counts). Tests assert positions exactly and compare triangle-sampled accessibility to within 2% only when the index hash differs.
- D-030 Master tooling set `fingerprint`, `sourceSignature` and piece `geometryVersion` are native deterministic tokens (D-026 class). Prior-set reuse works natively against native signatures only; the module-level planning and tooling caches of the reference are not ported (they are speed-ups, not behaviour).
- D-031 The native engine never claims an attempt it did not make: when the reference would retry a failed finalist with height-field tools, or fall back to multi-piece tooling, the engine records it in `unportedPaths` and leaves the attempt counters at the real number.
- D-032 The reference `constructCasePiece` core modes full-negative/full-positive release `removal` (aliasing `extendedTarget`) and then release `extendedTarget` again, so every attempt where the core overlaps the piece throws and is reported as `positive_piece_construction_failed`. Native reproduces the observable behaviour by default (`kReplicateReferenceCoreDeleteDefect` in MasterTooling.cpp) so results equal the reference; set it false to build the intended core-assigned pieces. Found by comparing native plans (which succeeded) with the reference (which could not) on the dumbbell; the cause was confirmed by running the reference with the same inputs.
- D-033 Manifold CrossSection (Clipper2) is enabled in the native kernel build; the reference binding builds a CrossSection from `Slice` with the positive fill rule, which `sliceOverlapArea` reproduces.
- D-034 Heavy equivalence rows (cube-grid-large, dumbbell, torus, cross-blind-holes, grooved-sphere) are skipped in Debug builds (QSKIP) and run in Release with QTEST_FUNCTION_TIMEOUT raised; CI must run the Release configuration of tst_master_equivalence.
- D-035 Master Mold runs as a cooperative thread-pool job (not a Web Worker). Cancellation and the 180 s timeout set a token the engine checks between steps; one in-flight Boolean cannot be interrupted, so cancel latency is bounded by the longest single operation. As in the reference, a cancelled run surfaces as an error status with "Master Mold generation was cancelled." (not a silent return to idle).
- D-036 The seed is built from the grounded part (identity transform, identity index because an STL is a triangle soup); the staleness identity covers part geometry, printer volume, process profile and preferences, never mold/cut/cavity state, as in the reference. Mold and Master displays share the scene body slots: whichever was shown last wins and a mold clear restores the Master pieces.
- D-038 The construction fallbacks run in the reference order: planar attempt, height-field retry of the same finalist, then (after all piece counts) region-direct grid partition, then multi-label reconstruction; attempt and parting-surface counters count real attempts. `unportedPathsReached` stays as a guard but nothing sets it now.
- D-039 New kernel seam methods `extrudePolygon` (CrossSection NonZero) and `transform` (3x4) back the ruled parting surface. The multi-label partition uses an exact three.js-style point-triangle distance (BVH of triangle boxes) and the engine `levelSet`.
- D-040 Engineering reports follow the reference faithfully, including its limits: the pull-direction candidate "analysis engine" is a scaffold and the completed session report is hard-coded sample data. Native ports both for equivalence but shows neither as a result; the UI card is fed by the real Python-ranked candidates run through the same ported completion/card/evaluation logic (`createPullDirectionReportFromCandidates`, a native generalization of the sample builder).
- D-041 `moldability_analysis` is a new worker command that runs the existing Python detailed mold analysis unchanged and wraps it in the standard `engineering_report` contract (status: completed -> success, partial -> partial with success true, blocked/failed -> failed with the blockers as errors, not run -> skipped). A model the engine cannot import is a failed report, not a worker error. Per-face lists (`face_evaluations`, `face_assessments`, `face_results`, `source_references`) are replaced by `<key>Count` and listed in `data.omitted`; the full report was 52 MB for a 10,800-face box.
- D-042 Reports from the worker are validated at the process boundary (`parseEngineeringReport`, a native addition): wrong schema/major version, unknown status or source, or malformed members make the whole report an error; nothing partially trusted is displayed.
- D-043 `localeCompare` for report ids and names is an approximation of ICU root collation for Latin text (`core/reports/LocaleCompare`): punctuation < digits < letters, base letter first, then accent, then case. It reproduces the reference order on the fixtures; non-Latin scripts compare by code point.
- D-044 Cavity analysis and generation readiness are wired into the existing `moldability_analysis` worker command instead of new commands: they cost a fraction of the detailed stage they depend on (0.06 s vs 2.7 s on a 768-face box) and recomputing that stage per command would multiply the dominant cost. A stage that raises is recorded under `data.stageErrors`, turns the report `partial` and adds a `CAVITY_ANALYSIS_FAILED` / `GENERATION_READINESS_FAILED` warning; it never hides the moldability result (py_worker_stage_failures).
- D-045 The readiness adapter is ported guard for guard (`isString` requires a non-empty trimmed string, an absent key is not `null`, unknown report statuses fall through). Its outputs are compared against the real TS adapter on real Python reports plus synthetic edge cases. Passthrough values (`direction` with extra keys, `faceCountBy*`) are copied as-is, as the reference does. Non-string entries in `warning_codes` / `blocker_codes` are dropped (the reference would stringify them into messages); the engine only emits strings.
- D-046 Project persistence is new native design (the reference frontend has none). A project stores inputs and records which derived stages existed; mold bodies, segmentation pieces, Master sets and reports are rebuilt (mold, executed segmentation) or left on demand (Master, reports). Determinism makes this safe and a test asserts rebuilt volumes equal the originals; it also keeps files small and avoids results that disagree with their inputs.
- D-047 One file, custom container (header, asset blobs, JSON manifest, footer with SHA-256 and length) rather than a ZIP: Qt has no public zip writer, and the format needs per-asset hashes, truncation detection and a streamable large asset. Format and policy are specified in PROJECT_FORMAT.md. The major version is the compatibility contract; newer minors preserve unknown members; migrations are a registered chain (empty at 1.0).
- D-048 The embedded model is a canonical binary STL of the source triangles (exact float32 round trip, identical geometry fingerprint), not the user's original bytes: the app does not keep them and re-reading the original at save time could disagree with what is loaded.
- D-049 Saving is atomic (`QSaveFile`) and keeps one `.bak` of the previous file only when that file is intact. Autosave goes to a separate per-project file, never the project's own; a normal save or a clean exit deletes it, an exit with unsaved changes keeps it.
- D-050 "Unsaved changes" compares inputs only (ids, timestamps, camera and derived-stage flags excluded), so orbiting the camera or generating a mold never prompts, while any edit or view-option change does. Importing an STL starts a new unsaved project; closing the window or replacing the document with unsaved changes asks first.
- D-037 When the engine reports `unportedPathsReached`, the panel says so ("This result may be missing options the full planner would try") instead of presenting the result as complete.
- D-051 The analysis runtime is the official embeddable CPython 3.13.17 zip from python.org, pinned by URL and SHA-256 in `native/packaging/pins.json` and bundled unchanged next to the app (`python/`). The engine is pure Python with no third-party packages, so there is no pip step. The SHA-256 was recorded at first download (trust on first use) and must be compared with python.org before a public release.
- D-052 Interpreter isolation is by construction: `python313._pth` (`python313.zip`, `.`, `..\analysis\site`) makes the interpreter ignore PYTHONPATH, PYTHONHOME, the registry and the user's site-packages, so the bundled engine cannot be shadowed and the user's Python cannot be affected. The app resolves the bundled runtime relative to its own directory; `CRAFT_PYTHON` still overrides it (developer use), and the verifier clears it.
- D-053 Development fallbacks are compiled out of shipped binaries: `CRAFT_EMBED_DEV_RUNTIME_PATHS` (ON for development builds, OFF in the `windows-package` preset). Found by a mutation test: with the bundled runtime removed, a packaged build silently used the baked-in development interpreter. A packaged app with no runtime now fails with `analysis_runtime_missing`, and the verifier also checks the executable for a baked-in development path.
- D-054 The engine is installed with `dist-info` metadata (so `importlib.metadata` reports its version) and precompiled to hash-based `.pyc` files that are never re-validated (`unchecked-hash`), because the install tree is immutable and may be read-only; the app writes nothing into it.
- D-055 The installer is deferred, not faked: the portable ZIP is the only distributable. An MSI (CPack WiX, per-user scope) needs the WiX Toolset, which is not installed here and could not be fetched with the permissions of this session. The install layout does not depend on the installer technology.
- D-056 Master tooling export is a new native feature, not a port: the reference frontend has no export for Master pieces (it only shows them). The contract is defined here and in `io/tooling/MasterToolingExport.h`: binary STL (millimeters, Z-up, the viewport's world frame) per piece, plus `manifest.json` (`craft.master-tooling-export` v1) with per-file SHA-256, bounds, volume, engine flags, release directions/sequence, registration pins, the excluded items with reasons, warnings, and the engine's "may be incomplete" flag (`unportedPathsReached`).
- D-057 What is exported: every piece of every tooling set whose status is `current`, independent of viewport visibility. Stale sets (the part or printer context changed) and blocked sets are never written; they are listed under `excluded` with the reason, and an export with nothing exportable fails with those reasons. Pieces the engine flagged (not watertight, not manifold, larger than the build volume) are exported with a warning rather than withheld, because the user may still want them.
- D-058 An export never overwrites anything: it goes into a fresh sub-folder `<model>_master_tooling[_N]` of the chosen folder, built in `<name>.craft-export-tmp`, verified by reading every file back (size, SHA-256, parsed triangle count) and then renamed into place. A failure or cancellation removes the temporary folder, so a folder with the final name is always complete. File names keep non-Latin letters, replace characters Windows/macOS forbid, and are made unique case-insensitively.
- D-059 Pieces are written exactly as the engine holds them: no re-orientation for printing, no supports, no unit change. That is a slicer/print-prep decision the manifest does not make for the user (its `releaseDirection` fields say which way each piece pulls).
- D-060 "Face selection" in the reference is the six faces of the part's selection box (front +Y, back -Y, left -X, right +X, top +Z, bottom -Z), not patches of the part's own surface: the reference highlights the whole model and lets the user hover and click box faces to toggle Cut by Face planes. The native port does exactly that; it does not invent a surface-region highlight. (The earlier checklist line "face-region selection highlight" misdescribed the reference.) The box face is resolved as the nearest ray hit among the six quads, each split into two triangles intersected double-sided with Three.js's rules, verified against the real reference on 188 rays.
- D-061 Selection scope: only the part is highlighted (the reference cannot select mold bodies). Native keeps its extra pick information (triangle, point, normal) in the inspector and still reports a click on a mold body, without highlighting it. Native has no "Cut by Face tab", so face toggling is active whenever the box is visible, the tool is Select and no segmentation owns the part; the box is visible while the part is selected and the mold is neither generating nor complete (the reference's rule). A click inside the box but off the part keeps the selection, as in the reference.
- D-062 Deliberate rendering differences: the face overlays are lifted off the box along their normal (`max(0.005, 0.0005 x diagonal)` mm) instead of the reference's polygon offset, which Qt Quick 3D lacks; the dash pattern uses the reference's 0.35/0.22 and, like Three.js's `computeLineDistances`, runs on from edge to edge (found by the equivalence test); a press that moves farther than 4 px (Euclidean, as the reference, not the former Manhattan rule) is a drag. The highlight colour rule uses linear-space lightness as Three.js colour management does, so the light/dark switch sits near sRGB 0xbc rather than 0x80.
- D-063 The Sprue 3D preview is the reference's three Three.js `CylinderGeometry` solids (funnel 5 mm tall with a 4 mm inlet radius, main stem, entry neck), reproduced vertex for vertex: native `cylinderSurface` ports the geometry's vertex order, normals and indices, `Quaternion.setFromUnitVectors` and `Matrix4.compose`, and the normals go through the renderer's normal matrix. The three solids are drawn as one mesh with the reference's material (green 0x31975a valid, red 0xb33a36 invalid, opacity 0.86, roughness 0.44, depth write on). A stem shorter than 1e-4 mm hides the preview; a main stem or neck shorter than that is hidden alone.
- D-064 Glass: while the Sprue tool is active on a complete mold, mold bodies are drawn at opacity 0.28 and outlined (dark red 0x762d34, opacity 0.78, 1 degree edge threshold, built on demand and freed when the tool changes); the reference's snapshot/restore of material state has no native counterpart because the look is a binding on the tool state. The preview hides when the pointer leaves, a button is held (orbit/pan), the tool or the mold changes, or a sprue is placed, and is recomputed at most every 16 ms.
- D-065 There is no sprue drag-move gizmo in the reference: `moveSprue` is a store action exercised by tests only, and the viewport's only sprue gizmo is the resize one (`sprueResizeRuntime.ts`). Nothing was invented: native keeps moving a sprue by coordinates in the inspector, and the earlier checklist line "drag-resize and drag-move gizmos" overstated the reference.
- D-066 The resize gizmo is ported with the reference's exact rules: rings (Three.js TorusGeometry, 8 x 32 segments) at the top opening and, once the sprue is resolved, at the entry-neck opening; the visible ring tube is max(0.12, 0.045 r), the pick ring max(0.45, 0.16 r) and front-face only; idle/hover/active colours and scales, pending and invalid sprues in their own colours; a drag changes the diameter by (dx - dy/4) x 0.05 mm snapped to 0.25 mm (Shift: free), normalised (2 to 50 mm, main >= neck, neck <= main); release commits only if the diameter changed; Escape reverts; double click opens a numeric editor whose input reads like a browser number field (anything unreadable is 0 and clamps to the minimum; a non-finite value is refused and the editor stays open). The rings follow the reference's presentation precedence: a pending intent shows its requested geometry only, resolved geometry otherwise, a failed intent without resolved geometry shows its own fields as invalid. The gizmo is active exactly when the Sprue tool is active on a complete mold (the same condition as the preview and the glass).
- D-067 Deliberate differences: the rings are drawn in a second transparent View3D with the same camera, which approximates the reference's depthTest:false + renderOrder 20 (a ring at the cavity stays visible behind the mold); the placement preview is hidden while the pointer is over a ring (the reference leaves a stale funnel there); the funnel cursor is the reference's SVG path drawn with QPainter and set on the viewport item; the diameter label and the numeric editor are QML overlays instead of DOM elements; hover and drag use the viewport item's pixel coordinates.
- D-068 The reference's Cut by Face "removal lifecycle" is the Eraser tool: the planes are drawn as slabs (cuttingPlane3dRuntime), the Eraser highlights one and a click calls `removeSplitFaceAndRebuild`, which removes the plane, rebuilds the mold parts without it, keeps the sprue definitions, drops the cavity and, when no plane is left, returns to face selection. (`removeSplitFace` is called by the cutting-session panel; `selectSplitFace` and `removeSelectedSplitFaceAndRebuild` have no UI caller at all, so they were not ported.) Native generates the mold in one step, so there is no separate "parts ready" stage to rebuild into: removing a plane here drops the generated mold, keeps the sprue intents and the other planes with their positions, and the user regenerates. The partition the reference would rebuild is the native reference mold's, whose body counts match the real store's for the removal scenarios.
- D-069 The slabs follow the reference exactly (0.02 mm thick along the axis, K2's extent on the other axes, centred on K2, at the plane's coordinate across K1; amber idle, red under the Eraser; double-sided, no depth write). They show while the mold is being set up or generating, and once it is complete only while the Eraser tool is active (the reference's `cuttingGuidesVisible`); native does not require the part to be selected for them to show (the reference draws them only while its selection box exists).
- D-070 Eraser rules: the tool is available only with cutting planes and not while the mold is generating (a mutating tool during an evaluation, as the reference); it falls back to Select when the planes vanish; a removal is refused while the mold is generating and for a face that is not cut; a removed plane forgets its position, so choosing the face again starts from the face's default, like the reference's removal then toggle. A click erases on release without a drag (the reference erases on press), so starting an orbit on a plane cannot remove it. Removals add no history entry because native has no undo/redo for Cut by Face (R-CutPlane-1).
- D-071 History is a list of snapshots like the reference (snap/history/undo/redo): a snapshot is pushed BEFORE each edit, undo restores it and pushes the current state onto redo, redo is symmetric, each stack keeps the last 50, a new edit clears redo, an edit that changes nothing adds no entry, and a gesture (begin/end around a slider drag) is one entry. The cut-face, clearance and sprue edits, the Eraser and a generated mold push entries. The step-by-step behaviour is replayed against the real store from `undo-reference.json`.
- D-072 A snapshot holds the inputs and the results built from them. The three large results (the mold, the sprue evaluation, the registration) are held through `Held<T>`, an immutable shared pointer with std::optional's read interface, so a snapshot costs a pointer and undo puts the very same objects back: the mold returns without recomputation (a test compares the result's address). Results are only ever replaced as a whole, never edited in place, which keeps every snapshot valid.
- D-073 Not in history: the model, the camera and tool, theme, selection, body visibility (not at first, recorded since D-113), segmentation and the Master Mold. Adopting or resetting a segmentation, importing a model and opening a project start a fresh history; the mold rebuilt when a project opens is not a step. Undoing past a generated mold returns to the inputs without a mold, so the user can undo "Generate mold" itself (in the reference generation is two steps with a parts-ready stage in between).
- D-074 Blocking and cancelling follow the reference: Undo/Redo are disabled while a sprue evaluation runs (generatingSprue) but not while a mold generates; undo or redo then cancels the generation (its late result is discarded by the generation counter). Edits made while a sprue evaluation is running are one burst and share the entry the first made (the reference's sprueHistoryBase). Native adds the Edit menu and the standard Ctrl+Z / Ctrl+Y keys.
- D-075 The project's model record gained an optional `sourceSizeBytes`: the size of the file the user imported. The reference builds the mold ids from the file name and size (`reference-mold:1:<name>:<size>:mold:N`), and an imported ASCII STL is embedded as a smaller canonical binary one, so a reopened project had a different size, different mold body ids, different geometry versions, and a different operation id in the header of every exported STL, with identical geometry. Reopening now restores the imported size, and the exported tooling of a reopened project is byte-for-byte the tooling exported before saving. The field is optional and additive (older files and linked models read as 0, meaning the stored file's size), so the format version is unchanged.
- D-076 The one thing an export may legitimately differ in is the `op=` field in the STL header, which carries the generation counter (`cavity-operation:N:`) as in the reference: a mold regenerated in a session after an edit is generation 2, the same project opened fresh is generation 1. The end-to-end test compares whole files across save and reopen, and triangles only (plus the header before `op=`) where a mold was regenerated in the session.
- D-077 A newly imported model is fitted from the CURRENT view direction, as the reference does (`localStlImport` calls `fitCameraToModel`, which keeps the direction from the target to the camera); only the Reset View command goes to the fixed (1, -1, 0.78) direction. Native used to reset the direction on every import, which put the first view a few degrees off the reference's (its starting camera looks along (95, -120, 73)) and discarded the user's view when another model was imported. Found by the viewport comparison; mask overlap on the box went from 0.82 to 0.89 before the later mask clean-up (0.99 after). Other refits (the mold appearing, segmentation, Master Mold) are native behaviour the reference does not have and were left alone.
- D-078 The pixel comparison measures what parity can mean between two different renderers: where the part lands (the mask of what changed between an empty frame and a frame with the part, thin marks removed by a 5 px opening and only the largest region kept: IoU, area ratio, centroid offset, boundary distance) and how the pixels inside it differ (SSIM, mean absolute difference). It does not claim pixel equality, which Three.js and Qt Quick 3D cannot give. Text panels and badges of the reference page are hidden in its frames; the native empty-state hint is hidden in its empty frame.
- D-079 Timing protocol: native uses swap-to-swap intervals of the real window taken on the render thread; the reference is timed in the page with a one-pixel readback as the GPU wait, both pipelined (N frames, one wait at the end) and synced (a wait every frame). Chrome's `gl.finish()` did not wait in these runs and a page loop alone times JavaScript, so neither is used. Every figure is measured twice, with the display's vsync (the cadence a user sees) and uncapped (the cost of a frame), in a Release build. No speed claim is made beyond the table in VIEWPORT_COMPARISON.md.
- D-080 The palette and lighting differences (the reference's part colours, background gradient, tone mapping, shadows, labelled grid, hint badge) are reported, not aligned. Matching them is a restyle that the comparison did not ask for; it is listed as open work with the exact reference constants in VIEWPORT_COMPARISON.md.
- D-081 The reference's part colour, mold colour and lighting do not depend on the theme in the running application. Frames rendered in the light theme show the dark theme's part and shading byte for byte, also after toggling the theme at runtime, although the code has a light variant of each (`resolveCadTheme`, the light lighting rig with key intensity 1.3 against 1.45; both recorded in look-reference.json). Native follows what the application shows: one part colour, one mold colour and one rig in both themes; only the background (`#0b1118` / `#f7f9fb`), the grid and the overlay text change. If the reference is fixed to use its light variants, `referenceLook` is the one place to change.
- D-082 The look is plain data in `core/view/ViewportLook`, taken from the reference's modules and pinned to them by a fixture generated from the real code (`craftLookReference.test.ts`, `tst_viewport_look`): part `#b8e3ec`, mold `#ba4a44`, roughness 0.38, metalness 0.06; the five-point rig; grid opacities 0.32 and 0.50; feature edges `#380f0e`, opacity 0.65, 25 degrees (an edge appears from a 26 degree bend), on mold bodies only. Values that need a WebGL context (exposure 0.95, environment intensity 0.55) are noted with their source file. The grid colours are what the frames show (the reference hands three.js colour strings it cannot parse in the dark theme, so its lines are white there). Qt specifics: ACES tone mapping; the background is a rectangle under a transparent 3D view, because Qt tone maps its clear colour; the lights are world-fixed with brightness I / pi times the exposure; the hemisphere light becomes an ambient term plus a light from above; the imported part is not outlined (no edge geometry is built for it, which is also why import got four to five times faster).
- D-083 The viewport bench moves its window to the fastest display and records which one it used. On a machine with a 75 Hz and a 60 Hz monitor the window opened on either, and a run on the 60 Hz one read 61 fps against 74.7 fps on the other: the display decides the cadence the swap chain is paced by. (D-080, which left the look unaligned, is superseded by D-081 and D-082.)
- D-084 The ground-plane ruler is ported from the reference's modules (core/view/GroundPlaneRuler) and replayed against the real runtime. - D-086 The Python engine's ray queries use a bounding-volume hierarchy (`geometry/ray_mesh_bvh.py`) instead of testing every ray against every triangle's box. It returns exactly what the brute-force scan returns, bit for bit: it prunes only with the very slab test the brute-force version applies to each triangle's box (on a box that contains the boxes below it, and rounding in that test is monotonic), never by hit distance (a hit within the epsilon can lie a hair outside its box); every remaining triangle gets the same box test and the same Moller-Trumbore arithmetic in the same order; ties go to the lowest face index like the ascending scan. `BruteForceRayMeshQuery` stays as the reference the tests compare against, and the three places that build a query use the hierarchy. This modifies the Python engine, which the migration had treated as an unmodified behavioural reference: the results are unchanged and that is what the tests, the field-by-field payload comparison and the stage fingerprints check; the engine's behaviour is still the reference.
- D-087 The candidate evaluation does what depends only on a face once for all candidates and runs one flat loop per candidate with the original arithmetic in the original order. `PullDirectionEvaluator(retain_face_evaluations=False)` is opt-in and used only by the worker: the per-face evaluation objects (candidates x faces of them) are not built, the metrics, score, warnings and evaluability are computed identically in the same loop, and `face_evaluations` becomes an object that knows its length and raises `FaceEvaluationsNotRetainedError` on any item access (a LookupError, so iterating it cannot look like an empty list). A custom scoring policy needs the evaluations, so it keeps them. The default stays as the reference had it.
- D-088 The worker serializes the detailed and cavity reports in one pass (`serialize_compact`) with the engine's own serialization rules, writing `<key>Count` for an omitted per-face key where the list would have been and adding its length to `omitted`, instead of `to_dict()` followed by the compaction. Same dict, same key order, same counts (tested as JSON text against the two-step version, on real reports and on awkward values). `compact_detailed_report` stays as the reference. The reason: the generic `to_dict()` built millions of dicts that were dropped straight away, which was most of the job on a smooth mesh.
- D-089 The pull-direction candidate evaluation runs in a native kernel (`native/engines/analysis-kernels`, a plain-C-interface shared library `craft_analysis_kernels`) that the Python worker loads through ctypes, instead of a native reimplementation of the whole analysis or a change of what is computed. Reasons: it removes the candidates x faces cost that no Python change could, keeps the engine the single source of the report (the kernel returns only per-candidate sums; the metrics, warnings, evaluability and score are built by the engine's `finish_candidate_evaluation`, shared with the Python loop), and keeps crash isolation (the kernel lives in the worker process). It is bit-for-bit identical to the Python loop by construction (same operations in the same order, no fused multiply-add or fast-math, the release C runtime python.exe uses, threads split candidates and never the faces of one) and by a check at load that rejects the library on one differing bit and falls back to the engine's Python loop, with the reason logged and reported beside the report. It is an optimisation, never a requirement: the application locates it (bundled `analysis/` folder or the build tree, passed as `CRAFT_ANALYSIS_KERNELS`; an inherited value is removed), and a package without it, or a library that fails, gives the same report slower.
- D-090 The kernel library depends on nothing but the C runtime and `vcruntime140.dll` that the interpreter already loads: no C++ standard library objects, no exceptions, platform threads (Win32 or pthreads) instead of `std::thread`, always the release C runtime even in a debug build. A package that ships only the embeddable Python therefore needs nothing next to the library, and `asin` is the interpreter's own. `verify-install.ps1` loads the installed library in the bundled interpreter and requires the check to pass, and requires the application to have resolved it.
- D-091 The right-button plane drag is a port of the reference runtime's drag, not a redesign: the pointer ray is intersected with a plane through the dragged plane's axis that faces the camera (the view direction with its axis component removed, the camera's up vector with its axis component removed when that is nothing), the plane moves by the hit's displacement along the axis, nothing happens within 4 px (Euclidean) of the press and once it has moved it stays a drag, and the coordinate is clamped to K1 with the planes' inset. - D-098 No manufacturing-profile UI and no separate sizing-policy workflow for Registration, because the reference has neither. - D-099 The derived evaluation memoises each sprue, as the reference's `sprueResultCache` does (evaluateDerivedMold.ts). `SprueResultCache` keeps one record per operation id and, after every evaluation, holds exactly that evaluation's records; a failure is memoised like a success; a record is used only when its key matches: the mold revision (cavity signature and every upstream body's id and geometry version), the frame id, the operation id, the anchor, the inward direction and the three profile dimensions. Editing sprue k therefore reuses sprues 0..k-1 and regenerates k and everything after it (their bodies changed), and regenerating an unchanged mold reuses all of them. The key is a superset of what the reference keys on (it also has the frame id, which the reference forwards to generation but leaves out of its key), so it can only lose hits, never serve a wrong result. The cache is shared with the worker jobs under a mutex, because a superseded job can still be running when the next starts; it lives in the controller and is cleared when a new model is imported. `evaluateSprues` takes the cache as an optional pointer and returns identical results with or without it; the result reports hits and misses (shown in the mold summary).
- D-100 The Segmentation plan preview is keyed in the background, as the reference's `generateSegmentationPlanPreview` does: after every valid plan the unkeyed section bodies appear at once and a worker job runs the canonical registration over them (the automatic sizing policy and the source's protected regions, revision prefix `segmentation-preview-registration`); when it finishes and the plan is still the current one the same bodies are shown with their keys, without moving the camera. - D-101 The 3D drag of Segmentation extension planes is not ported yet, and what the reference does is recorded here so that it can be. - D-102 The two remaining Master Mold construction items are not parity gaps, so neither is worked on. - D-103 Leftovers of an interrupted autosave are removed once they are stale. A process killed while the autosave is being written leaves QSaveFile's temporary file next to it (`<id>.craft.<6 characters of [A-Za-z0-9]>`, a partial or complete copy of the project); every later write uses a new name, so before this nothing ever removed it and each crash leaked up to the size of the project. `AppController::removeStaleAutosaveTemps` (called at the start of every refresh of the recovery list, so at start-up and after each autosave) removes a file with exactly that name that has not been written to for two minutes. The rule is deliberately narrow: a younger file may be this or another running instance writing right now (on Windows removing it would fail anyway, elsewhere it would break that write), and nothing else in the folder is touched (not `.bak`, not other names, not other lengths). The two-minute wait means the leftover of a crash survives the first restart and goes with a later refresh in the same or a following session. Found by the crash drill, which is the evidence for the pair: the recovery itself (D-103's reason for existing) needed no change.
- D-104 Saving, opening and importing show their progress and can be cancelled. The three file jobs run on worker threads but showed only a status line and offered no stop, which for a model near the 512 MiB limit means a long wait with nothing to look at. The footer now shows the progress bar, the stage (reading, parsing, preparing, saving) and a Cancel button while one runs; `cancelProjectOperation` stops it. The stops are cooperative: `project::IoControl` (a cancel poll, a progress callback, a chunk size of 1 MiB) is honoured by the project writer, reader and linked-model loader, and `stl::readFileBytes` reads an STL in chunks; between the single-call steps (parsing, building the model) the job checks for a stop. What a stop leaves is fixed: a cancelled save leaves the project file exactly as it was and no temporary file (the last check is before the commit; after it the new file is the file, and a stop that arrives then is ignored); a cancelled open or import leaves the open document, or the empty state, untouched; none of them is reported as an error. Autosave is not cancellable and shows nothing (it is silent by design).
- D-105 The 512 MiB STL limit (D-004) stays, now measured, and a mold that cannot fit in free memory is refused before it starts. At the limit (10.73M triangles, 511.8 MiB) the application loads, builds and renders the part, saves and opens it as a project, and cancels each of those within about 50 ms (R-LargeStl-1); the over-limit file is refused in 2 s with the existing message. What does not scale is the mold: its peak memory is about 1.3 KB per triangle (1.6 GiB at 1.31M triangles, 3.1 at 2.64M, 6.3 at 5.20M, and past 9.2 GiB without finishing at 10.73M), so the file limit admits parts whose mold needs about 13 GiB. `generateMold` therefore estimates `estimateMoldPeakBytes` (1.5 KB per triangle plus 64 MiB: 15 % over the worst measurement), asks the operating system how much physical memory is free (`availablePhysicalMemoryBytes`: Windows and Linux; elsewhere 0 = unknown = never refuse) and, when the estimate is larger, emits an error with both numbers and `mold_memory_insufficient`, changing nothing. Refusing is deliberately conservative and has no override: a refused model can be run after closing other applications or simplified, and the alternative (a process that grows until the machine stalls) was observed. Lowering the file limit instead would block the models that do fit.
- D-106 A Master Mold run that cannot be stopped is given up, not waited for, and its memory is checked first. The engine cannot be interrupted inside a Boolean, so the 180 s timeout and the Cancel button only flagged a token and the application stayed busy (every other operation refuses while busy) until the Boolean returned; on the 82k to 1.3M-triangle spheres measured that was longer than 250 s. Now the timeout, a cancel and a reset release the UI at once (`abandonMasterRun`: the panel fails with the timeout or cancel message, the application is no longer busy) and the worker thread, cancelled, ends on its own with its result and progress reports ignored, as the reference's worker model does; a run cannot be started while such a thread is still ending (the panel says so: `windingDown`), because a second heavy job on top of it would double the load. Master Mold is also refused before it starts when its estimated memory (9 KB per triangle plus 64 MiB; observed 7 to 8 KB, and unlike the mold it depends on the geometry) exceeds what is free, with the same message shape as the mold (`master_memory_insufficient`, D-105). The timeout is a setting of the controller (default 180000 ms) so that it can be tested. The mold's Cancel has the same limitation and is not changed here.
- D-107 The mold generation gets the same release as Master Mold (D-106), for all three ways it is given up: the Cancel button, a change of an input (clearance, a cut plane, cavity quality) while it generates, and undo or redo. `abandonMoldRun` releases the application at once, cancels the token, counts the thread as an orphan and makes its completion and progress handlers do nothing; a new generation is refused until the orphan has ended and the Mold section says so (`moldWindingDown`). Before this a change of input left the application busy until the engine's Boolean returned (a clearance edit made while a large mold generated froze every other action), and the completion handler cleared `busy` before checking that its result was still wanted, so a late result could clear the busy state of work started in the meantime. Undo already released `busy` by hand; it now goes through the same function so the orphan is accounted for.
- D-108 Part orientation (Flip and automatic orientation) is ported from `partOrientation.store.ts`, `runtime/automaticModelOrientation.ts` and `localStlImport.ts applyPartOrientation`. The orientation is one unit quaternion applied to the model as imported; the source triangles are never modified. The rotated triangles are re-grounded (centred on XY, lowest point on Z = 0), so the rotation centre does not matter. `composePartFlip` (five world-axis quarter turns, normalisation with V8's `Math.hypot`, snapping within 1e-12, sign rule) and the six-candidate scorer (support area, then footprint, then height, with the reference's epsilons; the first of equals wins) are compared with the real TypeScript through `orientation-reference.json` (9 meshes, 480 flip steps, 45 oriented geometries compared float for float). Behaviour carried over: orientation is unavailable without a ready model, after anything has been generated from the model (mold, sprues, segmentation pieces) and while an engineering operation runs, with the reference's wording; a committed change starts the Cut by Face session over (faces, planes, history) and keeps the clearances (`clearForOrientationChange`); the orientation is reset when another model is imported; arrow keys flip only while the Flip tool is active, a held key flips once. FINDING: in the reference, `orientModel` (automatic orientation) is implemented and exported by `useViewportRuntime` but no component calls it, so a user of the reference can only Flip; native exposes "Auto orient" as an Inspector button anyway (a native addition, it scores the model as imported, so repeating it gives the same orientation). Native additions: Reset orientation, and the orientation is saved in the project (`model.orientation`, an optional member: absent means the identity, so the format stays 1.0 and no migration is needed; the geometry fingerprint check still guards a reader that ignores it). Known differences: the part's visibility toggle is not preserved across a flip (the reference keeps it), the flip rebuilds the grounded part on the UI thread (a 10.7M-triangle model was not timed), and the grounding translation of the unrotated import path is added in float (existing behaviour) while the oriented path adds it in double precision as three.js does.
- D-109 The Master tooling export also writes one 3MF, always, beside the per-piece STL files and the manifest. The reference has no tooling export at all, so this is a native contract: <model>_master_tooling.3mf holds every exported piece as a named object (<mold part> / <piece>) in the same millimetre, Z-up world frame as the STLs (the same encoder and validator as the mold-body 3MF, D-092). Only current sets are exported, exactly as for the STLs; the 3MF is written to the same temporary folder, read back byte for byte, and checked independently (package structure, millimetre unit, one build item and one object per piece, the piece's triangle count, indices in range, no degenerate triangles). A piece the engine itself flagged not watertight / not manifold is still exported (as its STL is) and may fail the closed-mesh check; a piece the engine called clean that the 3MF check finds open is reported as a warning in the result and the manifest, never hidden. The manifest gains an additive `threeMf` member (file, bytes, SHA-256, unit, object names); `formatVersion` stays 1. There is no format choice in the UI: the STLs stay the interchange files and the 3MF is the single-file option, so the cost is one more file per export. MasterExportOptions::write3mf defaults to false for library callers; the application sets it.
- D-110 Segmentation extension planes are drawn, dragged and erased in the 3D viewport, settling the three questions D-101 left open by reading the reference code (the reference was not run for this; every point below is a reading, and where the reading shows a defect the native behaviour is stated). (1) Clearance: the slab is the Cut by Face slab, K2 = 'createReferenceMoldBlockBounds(K1, clearance)' with the store's clearance (Viewport.tsx passes 'singletonClearanceMm'); native uses the same 'moldClearanceMm_' the segmentation snapshot is built from. (2) Frame: the plan's extension coordinate is in the mold frame ('aggregateBounds' is 'frameBounds.referenceMoldBlockBounds', the block starting at 0), the part is displayed shifted into that frame by 'partOffset' ('setMoldAssemblyOffset' moves the model root) and the planes are children of that root, so slab and displaced part share a frame. The reference converts the coordinate with 'worldToNormalizedPosition(selectionBoxBounds, ...)', the unshifted K1, which for a 100 mm clearance would clamp a mid-block boundary onto the part's top face; native draws the slab at the coordinate itself (the displayed part box is the K1 it is filed under), so the slab is where the plan cuts. (3) Eraser and undo: in the reference the Eraser ('removeSplitFaceAndRebuild') and the store's undo only touch the visual plane and leave the engine's boundary as it was (a plane that is gone but still cuts, or an undo that moves a plane without moving the cut). Native keeps the two together: erasing an extension slab removes the boundary from the plan, and adding, editing (numerically or by dragging) and removing a boundary are undo steps that restore the plan's boundary list (axes the plan no longer leaves free are dropped on restore). Carried over: the drag is the Cut by Face drag (right button, 4 px threshold, reference plane through the camera, clamped into K1 with its inset, one undo step, nothing when it is where it was); the commit forwards the clamped coordinate and never rejects on validity (the plan's own validation reports it); the drag only moves the slab until the release (a pure visual update, the plan is rebuilt once). Native choices: while a plan shows extension planes they take the planes over (the reference's Segmentation tab owns the planes while open), so the Cut by Face planes are not drawn and box-face clicks do not toggle faces until the last extension is removed; a boundary outside the part box (typed, or invalid) is drawn where it is; a drag is refused while the plan is executing.
- D-111 Segmentation merges the protected regions of a committed mold, as `readCurrentSegmentationSourceSnapshot` does, and this is compared with the real reference (`segmentation-source-reference.json`, 15 scenarios driven through the real split-face and model-bounds stores). The automatic whole-block source stays the printable subject; a committed mold only contributes regions: the cavity (`committed-cavity`), each resolved sprue (`committed-sprue:<id>`) and each generated registration feature (`committed-registration:<id>`), all advisory, ordered by id. They are merged only when there are some and the mold was built on the same block and the same selection box (within 1e-9): a mold on another block keeps the automatic source and its own "evidence incomplete" warning. The merged source keeps the automatic identity except the protected-region signature (so the plan ids change with the regions), takes the committed evidence, and carries both evidence warnings. A committed result that is stale (document revision or fingerprint changed, or the mold is being generated again) or structurally invalid (no bodies, empty or not watertight meshes) blocks planning with `stale_source_revision` / `invalid_authoritative_geometry`, and is not replaced by the automatic source. In practice the merge applies only when the mold clearance is at least the automatic 100 mm (the application default is 10 mm), exactly as in the reference. Native: `readSegmentationSource` (core/mold/Segmentation) is the reference function; `AppController::planSegmentation` hands it the committed mold read before anything is dropped (final bodies, cavity bounds and clearance, resolved sprues, generated keys), and the Inspector shows a one-line note with the number of regions (a native addition: the reference UI shows nothing of them). Known differences: planning still replaces the committed mold (the reference keeps it until a segmentation is adopted), a blocked plan leaves the mold in place, and a mold that is being generated is the only stale state native can reach (editing an input drops the mold, so a revision mismatch cannot occur).
- D-112 Mold bodies are drawn by the faces' roles, with the reference's glass appearance as a toggle. The reference builds each mold body with one material per face run (`moldBodyMesh3d.ts`): the outer mold's red (`#ba4a44`), the cavity's inner surface a deeper red (`#9b3934`), registration keys yellow (`#d4a338`) and sprue funnels yellow (`#dfad3c`), each with its own roughness and metalness; in the glass appearance (`MoldAppearanceToggle`, shown once the mold is complete) every role is one `MeshPhysicalMaterial` in the outer mold's colour (opacity 0.3, roughness 0.18, metalness 0.02, transmission 0.68, thickness 0.8, ior 1.45, no depth write). All of it is pinned to the real code (`look-reference.json`, `materials.roles` and `materials.glass`, `tst_viewport_look`). Native: a body that has a face run of another role than the outer mold is uploaded with a float colour per vertex, the linear-light factor that turns the outer mold's colour into the role's (`roleTint`, it exceeds 1 for the yellow keys), multiplying the one material's base colour (`PrincipledMaterial.vertexColorsEnabled`); bodies without such runs keep the plain 24-byte vertex. The glass appearance is the view option `moldGlass` (runtime only, like the reference's store; the Inspector shows a "Glass appearance" button while the mold is complete): opacity 0.3 blended, the glass roughness and metalness, role colours off. The Sprue tool's own glass (0.28) takes precedence, a stale Master piece stays at most 0.2, and the "Mold opacity" slider (a native addition: the reference has none and draws the solid mold opaque; native's default is 0.55) applies otherwise. Wireframe: the reference has no wireframe mode, so none is added (the Edges menu entry, feature edges on mold bodies, was already native). Known differences: glass is drawn without transmission (refraction needs a screen-texture pass; the Sprue glass makes the same choice), the per-role roughness and metalness differences are not applied (one material per body, 0.06 and 0.03 apart at most from the outer mold's), and a body with face runs is flat shaded where the reference computes smooth vertex normals on its indexed mesh.
- D-113 Hiding or showing a mold body is an undoable step, and a plane edit shows every body again, as in the reference (this reverses the choice in D-073, which kept visibility out of history). The reference keeps `bodyVisibility` in every snapshot and `setBodyVisibility` pushes an entry (an unchanged value does not); `invalidateCommittedTopology` resets the map whenever a plane is chosen, moved or removed (the Eraser and the drag included), while a clearance change keeps it (`invalidateForClearance` spreads the old state). - D-115 Paths of MAX_PATH (260) characters or more work, by giving every standard-library file call the extended-length form. Windows ships with long paths off (`LongPathsEnabled = 0`, also on this machine), and then `std::filesystem` and the C++ streams refuse a path of 260 characters or more; Qt's `QFile`, `QSaveFile` and `QDir` already prefix such paths themselves (the project and autosave code was never affected). Measured before the change, with a 300-character folder: the STL import and export, the 3MF export and the Master tooling export all failed, and so did the Python import and moldability analyses (the worker got the path as text and could not open it: "Model file does not exist"). A deep folder is realistic: a OneDrive or customer folder of 150 to 200 characters is under the limit, and the Master export then adds a folder and a descriptive file name to it. Fix: `io/path/ExtendedPath` (`extendedLength(path, reserve)`, `displayPath`): on Windows an absolute path that is, or with `reserve` more characters would be, within the limit is made absolute, normalised and given as `\\?\C:\...` (or `\\?\UNC\server\share\...`); shorter paths are returned exactly as given, so nothing changes for them. It is used at the entry of `stl::readFileBytes`, `stl::writeBinary`, `threemf::write` and `validateFile`, `writeMasterToolingExport` (reserve 230 for the folder and file names it adds; the folder and file paths it returns, and its messages, stay in the ordinary form, so the panel, the log and the manifest never show a `\\?\` prefix), the 3MF cleanup in the controller, and `AppPaths::pathForWorker` for the `sourcePath` handed to the Python worker (its `open()` accepts the prefixed form). The model's own `sourcePath`, shown names and saved project paths are not changed. Tested (tst_long_paths, 11 tests, and one workflow test: import, both analyses, mold, STL and 3MF export, save and reopen through a 300-character folder): the helper's cases, each format and the Master export on a long path, a network path short and long through the machine's own administrative share (`\\localhost\D$`, a real SMB path), a read-only target file (refused, the original kept, no half-written sibling), a folder that denies writing (an access-control entry; the export fails with its own code and leaves nothing); with the helper disabled, 4 of them and the workflow test fail, and with only the worker conversion disabled the analysis assertions fail.
- D-116 Keyboard use is examined with real key events and the focus defect R-UI-5 is fixed. `app_smoke_focus` (`--focus-events`) drives the real window: the first Tab from a fresh window lands on the toolbar's Open button; a sprue's slider, a Cut by face check box and slider, a segmentation extension's field (typed and confirmed with Enter) and a Master Mold piece's check box each keep the keyboard focus after they act; Tab goes round the whole window without a trap and every control that takes Tab is reached (47 stops in the audit, written next to the summary as JSON); every Qt Quick Controls stop shows a focus indicator (`visualFocus`) and the section headers draw their own ring; a modal dialog takes the focus, Tab stays inside it, Escape closes it and the control that had the focus gets it back; and every stop has an accessible name (an `Accessible.name`, a button's text, or its parent's). Before the fix, with the real window: Space on a Cut by face check box, an arrow key on a sprue slider, Enter in an extension field and Space on a Master piece all sent the focus to the Inspector's container (each reproduced by putting the old list back and caught by the test). Cause: the Inspector's Repeaters ran on `QVariantList` properties, which QML rebuilds from scratch whenever the property is re-read, so the control that had acted was destroyed. The delegates are unchanged (the one role is `modelData`). Unlabelled sliders and spin boxes (printer volume, mold clearance, mold opacity, cavity clearance, the cut-face and sprue sliders, the extension field) got `Accessible.name`; the audit fails on one without. Not examined: the menus by keyboard (mnemonics, arrow keys), the combo box's popup, the operating system's file dialogs, and what a screen reader says (the names are checked through Qt's accessibility interface and the control types, not with Narrator).
- D-117 The window is examined at other display scales, other text sizes and other window sizes, and what broke is fixed. Method: the UI tour and its layout lint run under `QT_SCALE_FACTOR` 1.25, 1.5 and 2 (clean), and under a new development option `--font-scale` that scales the application font the way Windows' Text size setting does (`QT_FONT_DPI` does not do that: it changes the display scale, the captures come out at the same size as scale 2). Found at 1.25 / 1.5 / 2.0 times the text: the toolbar went past the window (Undo, Redo and Master cut off at 125 %), the Cut by face check boxes were squeezed (a fixed 96 px) and cut their labels, the report labels that did not wrap widened the Inspector past its panel (35 px at 150 %), and at 200 % the Inspector was too narrow, check box labels were elided and the sprue sliders left the window. Fixes: the toolbar is a `Flow` (one line at the normal size, a second line when the buttons do not fit), the check box wraps its label and has a minimum width, the report labels wrap, the sprue and cut-face sliders have a minimum width, and the Inspector's preferred and minimum widths (and with them the window's minimum width) follow the text size (`FontMetrics.averageCharacterWidth`, 340 and 260 px at the normal size). The tour is clean at 1.0, 1.25, 1.5 and 2.0 times the text. The real-input smoke tests were found to be valid only at 100 % scale: they gave the platform device-independent positions where it takes native pixels (QTest's helpers convert), so every mouse test failed at any other scale; the harness now scales by the window's device pixel ratio (`injectMouse`, the wheel and drag-and-drop helpers), and all 14 pass at 100, 125, 150 and 200 %. A pixel-level check was added to the plane-drag test: the pixels that differ between a hovered and an idle frame (the plane as drawn) must be picked as a plane (95 % of the samples), at three display scales and after the window is resized to its minimum and up; the picking is not offset or stale at any of them. The pick ignores what is in front of a slab, as the reference's raycast does, so the picked area may be larger than the drawn one. Not covered: moving the window between monitors of different scale, a fractional scale on a real display (Qt's pass-through rounding is the default), the viewport's own overlay text (the grid numbers, the hint badge, the status line, which keep their pixel size when the system text grows), and Windows' high-contrast mode.

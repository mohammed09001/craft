# Decisions

- D-001 Renderer: Qt Quick 3D with custom geometry from `MeshGeometryAdapter`. No custom Dawn/Metal/Vulkan renderer; no measurements yet that would justify one.
- D-002 Toolchain baseline: Qt 6.8.3 msvc2022_64, MSVC 14.44 (VS 2022 Build Tools 17.14), CMake 4.4.3, Ninja, C++20, Manifold v3.5.1 (commit cc8a7f6; same release as the reference's manifold-3d 3.5.1), Python 3.13.17 for the worker.
- D-003 Manifold built without TBB and CrossSection (single-threaded like the WASM reference; no Clipper2).
- D-004 Native STL size cap is 512 MiB (reference 25 MiB, a browser limit).
- D-005 Geometry-version tokens hash bounds as float64 rather than JSON text; stable on native, not string-equal to reference tokens.
- D-006 (superseded in session 3) Positive cavity clearance is now ported; the only intentional deviation is that a cavity-outer-breakthrough blocker is reported with the reference's observable code `cavity_boolean_failed`.
- D-009 Manifold stays built without TBB. Level-set sampling is parallelised by the engine itself: the lattice Manifold samples is pre-evaluated on all cores into a dense cache (bit-exact position match, otherwise falls back to the SDF). Cancellation is polled every 1024 SDF evaluations by throwing from the callback; the first exception is rethrown after the workers join.
- D-010 The offset SDF is evaluated with a distance band (clearance + 4 lattice steps): beyond it only the sign is computed. LevelSet uses exact values only near the offset surface, and the equivalence tests confirm identical output.
- D-007 Analysis cancel/timeout kills the worker process; it restarts lazily.
- D-008 QML lives in `native/app/ui` (qmlcache cannot handle `../` paths).
- D-011 The derived body geometry-version token after a sprue is a native FNV hash over (upstream version, operation id, position, profile, mold revision); it is stable and input-sensitive but not string-equal to the reference token.
- D-012 A sprue can only be created where the placement ray reaches the cavity (the reference preview shows an invalid, red placement and the store would accept it; the native app refuses it with a status message).
- D-013 Sprue intents live in the controller, survive cavity regeneration (marked pending, re-resolved in the same job) and are dropped on a new import. The reference per-sprue result cache is not ported; sprue re-evaluation after an edit reruns every sprue.
- D-014 Ordering of bodies and of equal-area interfaces uses byte order of the id string; the reference uses localeCompare (ICU). They agree for the id shapes produced by the app (digits and punctuation differ only at the first differing character), and all 30 reference cases match; ids with letter case or accents could order differently.
- D-015 Registration ids hash the same strings as the reference, so interface and feature ids are equal to reference ids (JavaScript Number-to-string is reproduced in jsNumberToString). The dependency-snapshot revision and body version tokens are native digests (D-005).
- D-016 Registration always runs as the last derived stage, also with zero sprues and a single body; a non-generated registration is reported as a warning (same rule as the reference store).
- D-017 Segmentation ids hash canonical JSON with keys ordered by an ASCII approximation of ICU collation (case-insensitive primary, lowercase before uppercase on ties). All 18 reference cases reproduce the reference ids; non-ASCII or punctuation keys are not covered.
- D-018 Native Segmentation plans from the preliminary whole-block source only. Merging protected regions from a committed mold (readCurrentSegmentationSourceSnapshot) is not wired; the committed-region builder exists as `protectedRegionsOf()` and is tested only through the protected-region planning cases.
- D-019 An adopted Segmentation result replaces Cut by Face: the cavity, sprue and registration stages run on the segmented bodies with segmentation lineage (partition-coverage check off, automatic registration sizing), and the mold clearance used is the automatic one (at least 100 mm).
- D-020 Plan preview shows planned section boxes only; the reference additionally generates a preview registration asynchronously.
- D-021 Planning-mesh cluster keys ("cx:cy:cz:face") are ordered with an ICU-like rule where ":" sorts before digits, to match the reference localeCompare; Math.hypot is reproduced with V8 compensated summation (`jsHypot3`) so normals agree to the last digit.
- D-022 Master preflight does not yet run the bounded self-intersection pass (a BVH triangle-pair test with three-mesh-bvh semantics). `selfIntersectionChecked` is therefore always false natively, so a self-intersecting mesh that the reference rejects is reported as valid or repairable here. This must be closed before Master Mold results are trusted.
- D-022 (closed) The preflight self-intersection pass is now ported (sweep over overlapping triangle boxes + a port of the three-mesh-bvh triangle test); it matches the reference on the overlapping-box fixture and is skipped above 20,000 triangles exactly like the reference.
- D-023 Accessibility rays use a native median-split BVH with a padded slab test and the three.js Ray.intersectTriangle arithmetic, not three-mesh-bvh itself; hit sets are identical on all fixtures but a ray grazing a box boundary within 1e-6 mm could differ.
- D-024 `icuLess` approximates ICU root collation for ASCII ids (punctuation < digits < letters, case-insensitive then lowercase first); `jsToFixed` reproduces JS toFixed (round half up on the exact decimal expansion).
- D-025 The planner is a stateful class (WorkingMoldPieceCountSearch) instead of a closure; it copies the planning mesh and analysis it is given. Parting-interface ids are ordered with icuLess. JavaScript Map/Set insertion order is reproduced with vectors where it affects results (piece area votes, adjacency).
- D-026 Working-mold geometryVersion is a native deterministic token (hash of the mesh version, direction and release order), not the reference value, which hashes a JSON of typed arrays; it is a stale-detection identity (same class of deviation as D-005).
- D-027 The planar constructor maps a source-mesh rejection to the reference WASM text ("Not manifold") so rejection reasons are identical; other kernel statuses keep their native wording.
- D-028 `tst_master_equivalence/constructionMatchesReference(cube-grid-large)` is skipped in Debug builds (QSKIP under !NDEBUG): a 50,700-triangle part makes every sweep a full Boolean and the Debug kernel exceeds Qt's 300 s per-test limit. It passes in Release (about 50 s for all construction rows). CI must run the Release build of this test.
- D-029 Kernel triangulation: native Manifold 3.5.1 and the WASM 3.5.1 produce bit-identical vertex positions on every Master piece, but on pieces with pin faces (coplanar faces with holes) the TRIANGLE CONNECTIVITY can differ (same vertices and counts). Tests assert positions exactly and compare triangle-sampled accessibility to within 2% only when the index hash differs.
- D-030 Master tooling set `fingerprint`, `sourceSignature` and piece `geometryVersion` are native deterministic tokens (D-026 class). Prior-set reuse works natively against native signatures only; the module-level planning and tooling caches of the reference are not ported (they are speed-ups, not behaviour).
- D-031 The native engine never claims an attempt it did not make: when the reference would retry a failed finalist with height-field tools, or fall back to multi-piece tooling, the engine records it in `unportedPaths` and leaves the attempt counters at the real number.
- D-032 The reference `constructCasePiece` core modes full-negative/full-positive release `removal` (aliasing `extendedTarget`) and then release `extendedTarget` again, so every attempt where the core overlaps the piece throws and is reported as `positive_piece_construction_failed`. Native reproduces the observable behaviour by default (`kReplicateReferenceCoreDeleteDefect` in MasterTooling.cpp) so results equal the reference; set it false to build the intended core-assigned pieces. Found by comparing native plans (which succeeded) with the reference (which could not) on the dumbbell; the cause was confirmed by running the reference with the same inputs.
- D-033 Manifold CrossSection (Clipper2) is enabled in the native kernel build; the reference binding builds a CrossSection from `Slice` with the positive fill rule, which `sliceOverlapArea` reproduces.
- D-034 Heavy equivalence rows (cube-grid-large, dumbbell, torus, cross-blind-holes, grooved-sphere) are skipped in Debug builds (QSKIP) and run in Release with QTEST_FUNCTION_TIMEOUT raised; CI must run the Release configuration of tst_master_equivalence.
- D-035 Master Mold runs as a cooperative thread-pool job (not a Web Worker). Cancellation and the 180 s timeout set a token the engine checks between steps; one in-flight Boolean cannot be interrupted, so cancel latency is bounded by the longest single operation. As in the reference, a cancelled run surfaces as an error status with "Master Mold generation was cancelled." (not a silent return to idle).
- D-036 The seed is built from the grounded part (identity transform, identity index because an STL is a triangle soup); the staleness identity covers part geometry, printer volume, process profile and preferences, never mold/cut/cavity state, as in the reference. Mold and Master displays share the scene body slots: whichever was shown last wins and a mold clear restores the Master pieces.
- D-038 The construction fallbacks run in the reference order: planar attempt, height-field retry of the same finalist, then (after all piece counts) region-direct grid partition, then multi-label reconstruction; attempt and parting-surface counters count real attempts. `unportedPathsReached` stays as a guard but nothing sets it now.
- D-039 New kernel seam methods `extrudePolygon` (CrossSection NonZero) and `transform` (3x4) back the ruled parting surface. The multi-label partition uses an exact three.js-style point-triangle distance (BVH of triangle boxes) and the engine `levelSet`.
- D-040 Engineering reports follow the reference faithfully, including its limits: the pull-direction candidate "analysis engine" is a scaffold and the completed session report is hard-coded sample data. Native ports both for equivalence but shows neither as a result; the UI card is fed by the real Python-ranked candidates run through the same ported completion/card/evaluation logic (`createPullDirectionReportFromCandidates`, a native generalization of the sample builder).
- D-041 `moldability_analysis` is a new worker command that runs the existing Python detailed mold analysis unchanged and wraps it in the standard `engineering_report` contract (status: completed -> success, partial -> partial with success true, blocked/failed -> failed with the blockers as errors, not run -> skipped). A model the engine cannot import is a failed report, not a worker error. Per-face lists (`face_evaluations`, `face_assessments`, `face_results`, `source_references`) are replaced by `<key>Count` and listed in `data.omitted`; the full report was 52 MB for a 10,800-face box.
- D-042 Reports from the worker are validated at the process boundary (`parseEngineeringReport`, a native addition): wrong schema/major version, unknown status or source, or malformed members make the whole report an error; nothing partially trusted is displayed.
- D-043 `localeCompare` for report ids and names is an approximation of ICU root collation for Latin text (`core/reports/LocaleCompare`): punctuation < digits < letters, base letter first, then accent, then case. It reproduces the reference order on the fixtures; non-Latin scripts compare by code point.
- D-044 Cavity analysis and generation readiness are wired into the existing `moldability_analysis` worker command instead of new commands: they cost a fraction of the detailed stage they depend on (0.06 s vs 2.7 s on a 768-face box) and recomputing that stage per command would multiply the dominant cost. A stage that raises is recorded under `data.stageErrors`, turns the report `partial` and adds a `CAVITY_ANALYSIS_FAILED` / `GENERATION_READINESS_FAILED` warning; it never hides the moldability result (py_worker_stage_failures).
- D-045 The readiness adapter is ported guard for guard (`isString` requires a non-empty trimmed string, an absent key is not `null`, unknown report statuses fall through). Its outputs are compared against the real TS adapter on real Python reports plus synthetic edge cases. Passthrough values (`direction` with extra keys, `faceCountBy*`) are copied as-is, as the reference does. Non-string entries in `warning_codes` / `blocker_codes` are dropped (the reference would stringify them into messages); the engine only emits strings.
- D-046 Project persistence is new native design (the reference frontend has none). A project stores inputs and records which derived stages existed; mold bodies, segmentation pieces, Master sets and reports are rebuilt (mold, executed segmentation) or left on demand (Master, reports). Determinism makes this safe and a test asserts rebuilt volumes equal the originals; it also keeps files small and avoids results that disagree with their inputs.
- D-047 One file, custom container (header, asset blobs, JSON manifest, footer with SHA-256 and length) rather than a ZIP: Qt has no public zip writer, and the format needs per-asset hashes, truncation detection and a streamable large asset. Format and policy are specified in PROJECT_FORMAT.md. The major version is the compatibility contract; newer minors preserve unknown members; migrations are a registered chain (empty at 1.0).
- D-048 The embedded model is a canonical binary STL of the source triangles (exact float32 round trip, identical geometry fingerprint), not the user's original bytes: the app does not keep them and re-reading the original at save time could disagree with what is loaded.
- D-049 Saving is atomic (`QSaveFile`) and keeps one `.bak` of the previous file only when that file is intact. Autosave goes to a separate per-project file, never the project's own; a normal save or a clean exit deletes it, an exit with unsaved changes keeps it.
- D-050 "Unsaved changes" compares inputs only (ids, timestamps, camera and derived-stage flags excluded), so orbiting the camera or generating a mold never prompts, while any edit or view-option change does. Importing an STL starts a new unsaved project; closing the window or replacing the document with unsaved changes asks first.
- D-037 When the engine reports `unportedPathsReached`, the panel says so ("This result may be missing options the full planner would try") instead of presenting the result as complete.
- D-051 The analysis runtime is the official embeddable CPython 3.13.17 zip from python.org, pinned by URL and SHA-256 in `native/packaging/pins.json` and bundled unchanged next to the app (`python/`). The engine is pure Python with no third-party packages, so there is no pip step. The SHA-256 was recorded at first download (trust on first use) and must be compared with python.org before a public release.
- D-052 Interpreter isolation is by construction: `python313._pth` (`python313.zip`, `.`, `..\analysis\site`) makes the interpreter ignore PYTHONPATH, PYTHONHOME, the registry and the user's site-packages, so the bundled engine cannot be shadowed and the user's Python cannot be affected. The app resolves the bundled runtime relative to its own directory; `CRAFT_PYTHON` still overrides it (developer use), and the verifier clears it.
- D-053 Development fallbacks are compiled out of shipped binaries: `CRAFT_EMBED_DEV_RUNTIME_PATHS` (ON for development builds, OFF in the `windows-package` preset). Found by a mutation test: with the bundled runtime removed, a packaged build silently used the baked-in development interpreter. A packaged app with no runtime now fails with `analysis_runtime_missing`, and the verifier also checks the executable for a baked-in development path.
- D-054 The engine is installed with `dist-info` metadata (so `importlib.metadata` reports its version) and precompiled to hash-based `.pyc` files that are never re-validated (`unchecked-hash`), because the install tree is immutable and may be read-only; the app writes nothing into it.
- D-055 The installer is deferred, not faked: the portable ZIP is the only distributable. An MSI (CPack WiX, per-user scope) needs the WiX Toolset, which is not installed here and could not be fetched with the permissions of this session. The install layout does not depend on the installer technology.
- D-056 Master tooling export is a new native feature, not a port: the reference frontend has no export for Master pieces (it only shows them). The contract is defined here and in `io/tooling/MasterToolingExport.h`: binary STL (millimeters, Z-up, the viewport's world frame) per piece, plus `manifest.json` (`craft.master-tooling-export` v1) with per-file SHA-256, bounds, volume, engine flags, release directions/sequence, registration pins, the excluded items with reasons, warnings, and the engine's "may be incomplete" flag (`unportedPathsReached`).
- D-057 What is exported: every piece of every tooling set whose status is `current`, independent of viewport visibility. Stale sets (the part or printer context changed) and blocked sets are never written; they are listed under `excluded` with the reason, and an export with nothing exportable fails with those reasons. Pieces the engine flagged (not watertight, not manifold, larger than the build volume) are exported with a warning rather than withheld, because the user may still want them.
- D-058 An export never overwrites anything: it goes into a fresh sub-folder `<model>_master_tooling[_N]` of the chosen folder, built in `<name>.craft-export-tmp`, verified by reading every file back (size, SHA-256, parsed triangle count) and then renamed into place. A failure or cancellation removes the temporary folder, so a folder with the final name is always complete. File names keep non-Latin letters, replace characters Windows/macOS forbid, and are made unique case-insensitively.
- D-059 Pieces are written exactly as the engine holds them: no re-orientation for printing, no supports, no unit change. That is a slicer/print-prep decision the manifest does not make for the user (its `releaseDirection` fields say which way each piece pulls).
- D-060 "Face selection" in the reference is the six faces of the part's selection box (front +Y, back -Y, left -X, right +X, top +Z, bottom -Z), not patches of the part's own surface: the reference highlights the whole model and lets the user hover and click box faces to toggle Cut by Face planes. The native port does exactly that; it does not invent a surface-region highlight. (The earlier checklist line "face-region selection highlight" misdescribed the reference.) The box face is resolved as the nearest ray hit among the six quads, each split into two triangles intersected double-sided with Three.js's rules, verified against the real reference on 188 rays.
- D-061 Selection scope: only the part is highlighted (the reference cannot select mold bodies). Native keeps its extra pick information (triangle, point, normal) in the inspector and still reports a click on a mold body, without highlighting it. Native has no "Cut by Face tab", so face toggling is active whenever the box is visible, the tool is Select and no segmentation owns the part; the box is visible while the part is selected and the mold is neither generating nor complete (the reference's rule). A click inside the box but off the part keeps the selection, as in the reference.
- D-062 Deliberate rendering differences: the face overlays are lifted off the box along their normal (`max(0.005, 0.0005 x diagonal)` mm) instead of the reference's polygon offset, which Qt Quick 3D lacks; the dash pattern uses the reference's 0.35/0.22 and, like Three.js's `computeLineDistances`, runs on from edge to edge (found by the equivalence test); a press that moves farther than 4 px (Euclidean, as the reference, not the former Manhattan rule) is a drag. The highlight colour rule uses linear-space lightness as Three.js colour management does, so the light/dark switch sits near sRGB 0xbc rather than 0x80.- D-063 The Sprue 3D preview is the reference's three Three.js `CylinderGeometry` solids (funnel 5 mm tall with a 4 mm inlet radius, main stem, entry neck), reproduced vertex for vertex: native `cylinderSurface` ports the geometry's vertex order, normals and indices, `Quaternion.setFromUnitVectors` and `Matrix4.compose`, and the normals go through the renderer's normal matrix. The three solids are drawn as one mesh with the reference's material (green 0x31975a valid, red 0xb33a36 invalid, opacity 0.86, roughness 0.44, depth write on). A stem shorter than 1e-4 mm hides the preview; a main stem or neck shorter than that is hidden alone.
- D-064 Glass: while the Sprue tool is active on a complete mold, mold bodies are drawn at opacity 0.28 and outlined (dark red 0x762d34, opacity 0.78, 1 degree edge threshold, built on demand and freed when the tool changes); the reference's snapshot/restore of material state has no native counterpart because the look is a binding on the tool state. The preview hides when the pointer leaves, a button is held (orbit/pan), the tool or the mold changes, or a sprue is placed, and is recomputed at most every 16 ms.- D-065 There is no sprue drag-move gizmo in the reference: `moveSprue` is a store action exercised by tests only, and the viewport's only sprue gizmo is the resize one (`sprueResizeRuntime.ts`). Nothing was invented: native keeps moving a sprue by coordinates in the inspector, and the earlier checklist line "drag-resize and drag-move gizmos" overstated the reference.
- D-066 The resize gizmo is ported with the reference's exact rules: rings (Three.js TorusGeometry, 8 x 32 segments) at the top opening and, once the sprue is resolved, at the entry-neck opening; the visible ring tube is max(0.12, 0.045 r), the pick ring max(0.45, 0.16 r) and front-face only; idle/hover/active colours and scales, pending and invalid sprues in their own colours; a drag changes the diameter by (dx - dy/4) x 0.05 mm snapped to 0.25 mm (Shift: free), normalised (2 to 50 mm, main >= neck, neck <= main); release commits only if the diameter changed; Escape reverts; double click opens a numeric editor whose input reads like a browser number field (anything unreadable is 0 and clamps to the minimum; a non-finite value is refused and the editor stays open). The rings follow the reference's presentation precedence: a pending intent shows its requested geometry only, resolved geometry otherwise, a failed intent without resolved geometry shows its own fields as invalid. The gizmo is active exactly when the Sprue tool is active on a complete mold (the same condition as the preview and the glass).
- D-067 Deliberate differences: the rings are drawn in a second transparent View3D with the same camera, which approximates the reference's depthTest:false + renderOrder 20 (a ring at the cavity stays visible behind the mold); the placement preview is hidden while the pointer is over a ring (the reference leaves a stale funnel there); the funnel cursor is the reference's SVG path drawn with QPainter and set on the viewport item; the diameter label and the numeric editor are QML overlays instead of DOM elements; hover and drag use the viewport item's pixel coordinates.
